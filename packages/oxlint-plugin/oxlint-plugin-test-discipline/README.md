# @systemfsoftware/oxlint-plugin-test-discipline

Oxlint rules enforcing property-based test laws, test placement, and test naming hygiene.

## Rules

| Rule                                 | What it enforces                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `no-test-file-in-src`                | Under `src/`, the only sanctioned test file is a single-segment `<stem>.workflow.property.test.ts` inside a sanctioned test directory, plus the generated `schema-laws.test.ts` entry point. Every other test file is banned: a kernel, policy, or schema suite becomes an in-source `import.meta.vitest` block, and a public-surface test moves outside `src/` as a Gherkin behaviour test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `src-property-test-cell`             | A property test under `src/` must be a single-segment `<stem>.workflow.property.test.ts` beside the `<stem>.workflow.ts` it covers. A source file whose suffix names a cell listed in `cellsRequiringTest` must also carry an in-source vitest block; that list is empty by default.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `test-file-outside-tests-dir`        | A test file outside `src/` must live under `tests/`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `test-suffix-outside-src`            | Outside `src/`, a test file's name must match the lanes its imports select. The lane word is the dotted segment just before `.test.ts`: `conformance`, `differential` or `trace` for a file importing that harness (the most specific lane wins), `integration` for a file importing only the Gherkin harness, and `runner` for a file in a `vitest-runner` package that imports a Vitest runner module and no harness. A name for another lane (`laneMismatch`), a test whose imports select no lane (`noLane`), and a test whose only lane is the property lane (`propertyOutsideSrc`) are reported. The name triggers no requirement.                                                                                                                                                                                                                             |
| `tests-dir-helpers-in-fixtures`      | Under `tests/`, the only non-test modules are helpers and fixtures, and they live inside `tests/__fixtures__/`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `no-io-module-in-source-test`        | An in-source `import.meta.vitest` test block is forbidden in a module that performs I/O — decided from the module's own syntax (a non-type import from a filesystem, process or network module, called at least once), never from its filename. Only the in-source-test idiom is judged: a module whose tests live in separate files is a no-op for this rule.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `behaviour-test-requires-gherkin`    | Any test file that imports `@systemfsoftware/effect-gherkin-spec` must import `makeFeature` from it and build its suite through a Feature. Which runner it may import is owned by `vitest-from-systemfsoftware-vitest`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `behaviour-exercises-use-case`       | Any test file that imports `@systemfsoftware/effect-gherkin-spec` must import the package under test: a runtime import of something other than the runner, the Gherkin harness, `effect` (or a subpath), a Node builtin, or the file itself. Type-only imports never count.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `behaviour-one-feature-per-file`     | Any test file in the behaviour lane must contain exactly one `Feature(...)` call; zero or two-or-more is the junk-drawer signal.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `no-pseudo-gherkin-unit-tests`       | In any test file that imports `@systemfsoftware/effect-gherkin-spec`, every `Feature(...)` declares its environment with `.withLayer(layer)` or `.withScenarioLayer(layer)`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `differential-test-requires-harness` | Any test file that imports `@systemfsoftware/differential-spec` must invoke its harness (`Differential.compare({ name, reference, candidate })` or `Metamorphic.on({ name, system })`); importing it without invoking it is non-compliant, and raw `fc.assert`/`fc.check`/`fc.property`/`fc.asyncProperty` calls are refused because the harness owns fast-check.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `conformance-test-requires-harness`  | Any test file that imports `Conformance` from `@systemfsoftware/conformance-spec` must invoke one of its checks — `Conformance.linearizable`, `Conformance.sequential`, or `Conformance.released`. The retired `Linearizable.check` / `SequentialModel.check` / `Released.check` shapes are refused, and importing the barrel without invoking a check is non-compliant.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `trace-test-requires-taxonomy`       | Any test file that imports `@systemfsoftware/trace-spec` must terminate cases on relation holds over the declared span graph. Raw emit calls and HTTP status, statusText, or body assertions are forbidden. The trace lane is selected by this import; `*.trace.test.ts` is the naming convention for trace tests.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `model-fixture-imports-subject`      | A `*.model.ts` fixture may not import the package whose tests it serves. The package is read from the fixture's path — the directory its tests tree lives in — and an import, re-export, dynamic import, or require of that name, or of any subpath of it, is the implementation reaching its own oracle. A relative specifier is judged the same way lexically: resolved against the fixture's directory it must stay inside the tests tree, so `../../src/Lock.js` is reported and `./Locks.js` is a sibling fixture. `effect`, node builtins, and other packages' names stay allowed.                                                                                                                                                                                                                                                                             |
| `property-file-purity`               | A property file is found by content: a test file that imports FastCheck or calls `it.prop`/`it.effect.prop`, unless it is in the differential lane. A property file holds only property tests: no plain `it()`/`test()`/`it.effect()`, and no raw `fc.assert`/`fc.check`/`fc.property`/`fc.asyncProperty`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `vitest-from-systemfsoftware-vitest` | Every value a test uses from Vitest is imported from `@systemfsoftware/vitest`, which re-exports all of Vitest. Any value import from `vitest` or the upstream `@effect/vitest` — named, namespace, default, side-effect or dynamic — is refused; a type-only import stays legal. In the behaviour, conformance and differential lanes the harness owns the runner: each `it`/`test`/`describe` imported from any of the three sources is reported once, and in the conformance and differential lanes every other `it`/`test`/`describe` call, the Gherkin `it` included, is reported too. The trace lane owns no runner: a trace test calls `it`/`describe` from `@systemfsoftware/vitest`, and only the refusal of `vitest` and `@effect/vitest` value imports applies to it. A package declaring the `vitest-runner` role is not refused for raw Vitest imports. |
| `tests-import-public-api`            | Every file under the package-root `tests/` or `__tests__/` trees, regardless of basename, may not relative-import `src` or climb into an `internal` folder. Import the published package name or a sibling helper.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## Test Lanes

Which requirements apply to a test file is decided by what it imports and calls, never by its filename or folder. A file in several lanes meets every lane's requirements. Outside `src/` the name is checked against the lanes, never the reverse.

| Lane         | Selected by                                                                             | Name convention                    | Doubles                  | Location           |
| ------------ | --------------------------------------------------------------------------------------- | ---------------------------------- | ------------------------ | ------------------ |
| Property     | FastCheck import or `it.prop`/`it.effect.prop` call                                     | `<stem>.workflow.property.test.ts` | none — pure core         | ONLY under `src/`  |
| Behaviour    | Import from `@systemfsoftware/effect-gherkin-spec`                                      | `*.integration.test.ts`            | permitted, at ports only | NEVER under `src/` |
| Differential | Import from `@systemfsoftware/differential-spec`                                        | `*.differential.test.ts`           | permitted, at ports only | NEVER under `src/` |
| Trace        | Import from `@systemfsoftware/trace-spec`                                               | `*.trace.test.ts`                  | none — observes graphs   | NEVER under `src/` |
| Conformance  | Import from `@systemfsoftware/conformance-spec`                                         | `*.conformance.test.ts`            | permitted, at ports only | NEVER under `src/` |
| Runner       | A Vitest runner module, no harness, in a package that declares the `vitest-runner` role | `*.runner.test.ts`                 | n/a                      | NEVER under `src/` |

## The `vitest-runner` Role

Packages that are the test framework itself (today `packages/runner/vitest`, `packages/runner/vitest-conformance`, and `packages/effect-spec-runtime`) declare the `vitest-runner` role in their `oxlint.config.ts` using:

```ts
const RUNNER_ROLE: ['error', { role: 'vitest-runner' }] = ['error', { role: 'vitest-runner' }]
```

This constant is applied to both `@systemfsoftware/oxlint-plugin-test-discipline/vitest-from-systemfsoftware-vitest` and `.../test-suffix-outside-src`.

With the role declared, raw Vitest imports in that package are its own lane and are not refused by `vitest-from-systemfsoftware-vitest`. A test there that imports a Vitest runner module and no harness is in the runner lane, and `test-suffix-outside-src` requires the name `*.runner.test.ts`. Every other check still runs: a runner import inside a harness lane is still reported, and a Gherkin-driven test keeps the `integration` name. The same imports in a package that declares no role are refused and select no lane.

The role is a trust point: the linter cannot verify that a package actually is the runner framework. A package that declares the role without being the runner (for example a fixture package) is treated identically to the runner. Reviewers must check every change to the role declaration in config diffs.

## Enrollment

`@systemfsoftware/oxlint-config-recommended` loads this plugin in `jsPlugins` and spreads `configs.recommended` into its default `rules` at `error`, so every rule above fires in every package that extends the preset.

## `no-inline-suppression`

The package also ships a `no-inline-suppression` bin. It fails when a scanned file has a comment that opens with any of these, in line and block comments alike:

- `oxlint-disable`, `oxlint-disable-line`, `oxlint-disable-next-line`
- `eslint-disable`, `eslint-disable-line`, `eslint-disable-next-line`
- `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`

A word that only appears inside a string literal, or later in a comment's prose, is not a directive and passes.

It runs outside oxlint on purpose: oxlint obeys a disable directive even for a JS plugin rule that names it, so a rule could be switched off by the code it grades. The bin reads no configuration, and nothing inside a scanned file can exempt it.

```bash
no-inline-suppression            # every git-tracked .ts/.tsx/.mts/.cts/.js/.jsx/.mjs/.cjs file under the working directory
no-inline-suppression src/a.ts   # only the named files
```

Each finding prints as `file:line:column: <form> is forbidden. ...`. Exit status: `0` clean, `1` a refused comment or a file the parser could not read, `2` the files could not be listed or opened.

## Testing

Each rule ships a RuleTester suite at `src/rules/__tests__/<rule>.test.ts`, with 100% mutation coverage required.
