# AGENTS.md — `@systemfsoftware/stryker-js-plugin-api`

> **Location:** `packages/stryker-js/plugin-api/` — the plugin API of the @systemfsoftware Stryker fork.

Ported from `@stryker-mutator/api` v9.6.1; the upstream's idioms are kept outside the option set. The option set is this fork's own: one Effect Schema in `src/core/stryker-options.schema.ts` replaces the vendored `schema/stryker-core.json` + `json-schema-to-typescript` codegen chain (deleted), and the JSON Schema document consumers validate against is derived from it (no file read). The package is gated by `pnpm lint` (oxlint, shared config), `pnpm typecheck`, and `pnpm build`.

Deltas from root:

- **No `stryker.config.json`** — this is an API/types cell, so it decides nothing and must not be enrolled in mutation (root mutation rule — `check:mutate-scope`).
- **The one intentional divergence from the original.** `src/` carries exactly two edited files: `src/plugin/tokens.ts` gains `commonTokens.sandboxDirectory`, and `src/plugin/contexts.ts` gains the exported `SandboxPluginContext` interface (a `PluginContext` with `[commonTokens.sandboxDirectory]: string`). They exist so Stryker can hand the sandbox directory to plugins as an injected value instead of plugins inferring it from `process.cwd()`. The token is bound only in sandbox worker processes (test runners, checkers); plugins that run in the main process, such as reporters, must not inject it — core cannot supply it there.
- **The option set is ONE Effect Schema, derived — never generated.** `src/core/stryker-options.schema.ts` declares every option name, type, optionality and default, and nothing else: `strykerCoreSchema` is the JSON Schema document derived from it via `S.toJsonSchemaDocument` (no file read) and lives in `src/core/stryker-core-schema.ts`, because a document is a _use_ of a schema and a `*.schema.ts` exports only declarations — the gate is `schema-file-exports-schemas-only`, and a tool that reads every exported schema in the package (the generated law suite) breaks outright when handed a document. Both are re-exported from `src/core/index.ts`, so the published names are unchanged. There is no `schema/` directory, no `src-generated/`, no `generate` script, and no `json-schema-to-typescript`. Extend the schema module and the document follows; the gates are `pnpm lint`, `pnpm typecheck`, `pnpm build`.
- **`core.d.ts` is deleted.** The original ships it as a shim so `--moduleResolution node` can resolve `@stryker-mutator/api/core` for JSDoc `import('.../core')` type annotations. This package is ESM-only with a tsdown-generated exports map, so the `./core` subpath resolves through `exports`, and the shim's `./dist/src/core/index.js` target is a layout the tsdown build no longer produces.
- **Build layout is `dist/<subpath>/index.mjs`, not `dist/<subpath>.mjs`.** Kept for convention with the sibling forks; no entry has a runtime file dependency now, so the entries could be flattened without breaking the `core` subpath.
