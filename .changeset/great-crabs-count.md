"@systemfsoftware/alchemy-stack-layer": minor

New package. `alchemyStack(name, config)` returns a service tag, distinct for each stack name, whose service is the stack's outputs, with a `layer` that deploys the stack on `@alchemy.run/test`'s engine when acquired and destroys it when released. `config.deploy` takes a stack definition carrying its own `providers` and `state`, or a function that receives `deploy` and returns the outputs, with an optional `setup` layer for what that function needs; stacks are destroyed in reverse deploy order, and each is registered for destroy before its deploy starts. Dev mode and sidecar resolve as `@alchemy.run/test` resolves them; `dev`, `stage`, `sidecar` and `profile` are forwarded unchanged. Without a configured `stage`, the stage starts from a non-empty `ALCHEMY_TEST_STAGE`, otherwise from `test_$USER_<worktree>` when the working directory is inside a linked git worktree, as `@alchemy.run/test`'s runner names it, so two worktrees of one checkout never share a stage, and otherwise from `test_$USER`; it then gets `_` and 8 hex digits of the SHA-256 of the running test file's Vitest project name, root directory name and path from the root; `fileStage({ baseStage, testFile })` is exported to compute that stage outside a test. Before deploying, the layer destroys any deployment left at the stage; if that fails, acquiring fails with `StackDestroyFailed` and nothing new is deployed. A cloud deploy over local or in-memory state fails with `DurableStateRequired` before it deploys; a failed deploy fails with `StackDeployFailed` and a failed destroy with `StackDestroyFailed`, each naming the stack and the stage; a stack with no configured stage built outside a running test file, or whose `ALCHEMY_TEST_STAGE` cannot be read, fails with `StageUnresolved`. `alchemy`, `effect` and `@effect/platform-node` are peer dependencies.
