# @systemfsoftware/effect-e2e@1.2.0

The README now covers installing the package from the systemfsoftware flake tarball and its `effect` and `vitest` peers, the suite files `effect-e2e init` writes, what each of the eight entry points holds, and the `report-1` document with `report1JsonSchema()` from `./report`. It credits TesterArmy's `e2e`, from which the package ports source, and reproduces TesterArmy's Apache-2.0 NOTICE. The `./runner` entry exports `e2eRunShape(config, options)`. It decodes the config as the runner and the global setup do and returns `{ retry, maxWorkers }` from the config's `retries` and `workers`, or from the CI run shape (one retry, one worker) when neither is written. Spread it into the `test` block of the suite's Vitest config; a config the runner refuses yields an empty object. The runner documents one precedence rule: CLI flag > config > Vitest default, with a test's own `retries` option above every run-level value and `VITEST_MAX_WORKERS` above flag and config for the worker pool. A suite's runner and global setup apply `effect-e2e run`'s overrides from the composition root's `env`: `E2E_TARGET` keeps one target, `E2E_AGENT` makes the named agent the default, and `E2E_CACHE`, `E2E_TIMEOUT`, `E2E_OUTPUT` and `E2E_TRACE` replace cache mode, timeout, output and trace. An override naming no target or agent in the config, or a value outside its type, refuses the config with its key path. `RUN_OVERRIDE_ENV` names the variables. The global setup provides the run's output directory under `RUN_OUTPUT_KEY` and, for a refused config, the refusal under `RUN_REFUSAL_KEY` (both exported from `./runner`), so a host that runs Vitest in its own process can tell which report belongs to the run. A try that does not pass writes `ai-trace.json` into its result directory when ai-trace is on: the config's new `aiTrace` key (default `false`), or `E2E_AI_TRACE=true|false` in the run's environment (`RUN_OVERRIDE_ENV.aiTrace`), which overrides it; any other non-blank value refuses the config at `aiTrace`. The file (`schema: "ai-trace-1"`) lists every model call of the try with its step, the request with screenshots reduced to their byte count, and its outcome (`Answered`, `Failed`, `Interrupted` or `Died`), with every held secret masked as `[secret:<name>]`; it is written whatever the `trace` setting, `trace.md` links it, and a store that refuses it adds `ARTIFACT_WRITE_FAILED` to the attempt. A run with ai-trace off removes the `ai-trace.json` an earlier run left under `results/`.
