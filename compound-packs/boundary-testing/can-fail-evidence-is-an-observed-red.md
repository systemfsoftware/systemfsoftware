CONST-T3 asks that every test be able to fail when the behaviour it names breaks (`CONSTITUTION.md:90-95`). A claim that a test or a check can fail is evidence, and a reviewer has to be able to check it. A red the author saw after editing the code by hand, in the working tree, a scratch copy or a scratch clone, and then reverting, cannot be checked: nobody else can open the tree it ran on, and the author chose the edit. Breaking the code while writing a test is still a sound way for the author to learn whether the test can fail. Seemann's advice is to run each new test "and see it fail" ("Tautological assertion", https://blog.ploeh.dk/2019/10/14/tautological-assertion/). That is a working aid, not evidence for anyone else. Mutation runs only in CI on main (root `AGENTS.md` REPO-D3, `AGENTS.md:68`; `compound-packs/ci-wall-clock/mutation-runs-nightly-on-main.md`). `compound-packs/schema-laws/refusal-properties-cover-unobservable-boundaries.md:41` lists can-fail routes for a refusal property; where the two differ, this rule governs, and `:41` is re-pointed here once #769, which edits that file, lands.

## Rule

A change that claims a test or check can fail names a red that CI observed on a commit a reviewer can open, through one of three routes, or it states `red not shown`. In every route, the red is the claimed test or check failing, not another test of the same behaviour:

1. **Red on the real, unmodified pre-fix commit in CI.** The claimed test is added on its own over the pre-fix code, with no other edit, and CI runs it there and one of its own assertions fails. A red from failing to load, resolve or type-check, or from the CI run itself, is not this route; where the subject does not exist before the fix, route 1 is unavailable and route 2 applies. The claim names that commit and the CI run id. A generated-input property run that failed in CI on unmodified code is this route.
2. **A deliberate-red throwaway CI pull request.** A draft pull request breaks the code holding the behaviour and changes nothing else. The claim names the pull request and the id of the CI run in which the claimed test failed, and the pull request is closed unmerged.
3. **The Mutation lane on main**, its nightly run or a dispatch of that lane on main, named by the mutant id, the run id, and the test id that run's report records in the mutant's `killedBy` (the runner names a test `<file>#<test name>`). A report part rebuilt from a shard's event stream records no `killedBy`. For such a mutant, the route names two main runs instead, the last before the test merged showing the mutant surviving and a later one showing it killed, and it holds only when no other merge between those two runs changed a test file or the mutated file, so the claimed test is the only change that can account for the kill; otherwise the claim states `red not shown`. The report artifact is kept for 14 days (`.github/workflows/reusable-mutation.yml:394`), so the route holds only while the report a reviewer would open still exists. It exists only for a test already on main and a file the lane mutates (today, the workflow files the planner admits).

When no route applies, the change states `red not shown`, and the review weighs the test without that evidence.

- **No local probe as evidence.** A mutant applied by hand, a local edit and revert, a line changed in a scratch copy or a scratch clone, a value planted in a module, config or build output the package ships or installs, and the pre-fix source swapped in locally are never evidence that a test or check can fail. That holds whether the edit was reverted, described in the PR body, or carried through review. While working, the author may still break the code to see a test fail; the evidence is the red one of the three routes then shows. A body that mentions such a probe calls it a working aid and gives a route or `red not shown` beside it. The inversion loop in `docs/solutions/architecture-patterns/extraction-strands-the-origins-gate.md:63-70` (inject a negated predicate, observe red, restore) is that working aid; pushed as a deliberate-red pull request, its red is route 2. A gate, rule, plan or solution doc that a change adds or edits and that asks for can-fail evidence names one of the three routes. A dated plan nobody edits stays as the record it is.
- **A detector's planted fixture is a test input, not a mutant.** A lint rule, gate or guard is shipped code whose behaviour is to report a violation, so its test feeds it one: a `RuleTester` invalid case, a known-bad file in its fixture folder, a `--selftest` case whose input sits in that folder. Such a planted violation is can-fail evidence for that detector alone, and only when all of these hold. It is committed in the change, and CI runs the detector's test over it. It lives in that test's own inputs, the test file or a fixture folder under the test tree, never in a module, config, build output, lockfile, patch or dependency that the product ships or installs. Only the detector's test reads it. The claim names the fixture path and the CI run. It shows nothing about whether any other test can fail. A product test run against an edited copy of product code is a mutant whatever folder holds the copy, and so is an edit to the detector itself, such as a deleted branch or a weakened pattern: its red goes through route 2.
- **The vendored constitution says otherwise until upstream changes.** Its CONST-T10 criterion "Sabotage after green: break one core law and one published field; at least one test goes red" (`repos/constitution/ENFORCEMENT.md:214`) prescribes the hand-applied route. That file is read-only here (root `AGENTS.md` REPO-S3), and this repository has already decided to delete the sentence (`docs/plans/2026-10-13-0612-refactor-retire-generated-schema-laws-plan.md:147`). Until the deletion lands upstream, this rule governs changes in this repository.

```text
# WRONG: systemfsoftware/systemfsoftware #56 body (merged 5645a62eed, 2026-08-05)
In place of a Stryker run, each of the seven kernel mutants below was applied by hand and the suite re-run:
killed  maxDepth 2 -> 3 (cap raised)              -> ∀e_ExprNesting_≤DepthCap

# RIGHT: neutral shape, no citation
Can fail: test-only commit <sha> adds ∀e_ExprNesting_≤DepthCap over the unmodified pre-fix code; it failed in CI run <run id>.
Can fail: draft pull request #<n> raises the cap to 3 and nothing else; ∀e_ExprNesting_≤DepthCap failed in CI run <run id>, and the pull request was closed unmerged.
Can fail: the rule's test reports the committed fixture tests/fixtures/planted-effect.tsx in CI run <run id>.
```

Incidents. Pull request bodies in this organisation have offered a local probe as the evidence that a test or check can fail, and kept it through review rounds. In systemfsoftware/systemfsoftware, #56 (`5645a62eed`, 2026-08-05) offered seven kernel mutants applied by hand in place of a Stryker run. #761 (`0923912eed`, 2026-10-13) deleted a pack gate that asked a reviewer to "check it by widening the refinement locally once" (`5965b034b5:compound-packs/schema-laws/refusals-beside-generated-laws.md:52`), because widening by hand is a hand-applied mutant (`docs/plans/2026-10-13-0612-refactor-retire-generated-schema-laws-plan.md:135`). Within two days in October, four more bodies did the same. systemfsoftware/gritlint #20 (2026-10-12) cited line edits in a scratch copy as red probes. systemfsoftware/systemfsoftware #763 (2026-10-13) cited a removed release call as the failing scenario. systemfsoftware/pnpm-release-management #64 (2026-10-13) cited a mutant in a scratch clone as "falsification". systemfsoftware/systemfsoftware #737 (2026-10-13) cited a planted invalid option and a case arm deleted in a scratch copy. Three of the four bodies withdrew the probe before merge. Two of the four scenarios were then shown red through the routes above: #64 cites a CI run of its test over the unmodified pre-fix code, and #763's scenario failed in the deliberate-red pull request #764, closed unmerged.

Gate: `review` — Does the diff, its plan, its PR body or a commit message claim that a test or check can fail on the strength of a mutant applied by hand, a local edit and revert, a scratch copy or clone, a value planted in a module, config or build output the package ships or installs, or the pre-fix source swapped in locally? Does a gate, rule, plan or solution doc the diff adds or changes prescribe editing code by hand to show a red? Does a can-fail claim lack a CI run in which an assertion of the claimed test failed over the unmodified pre-fix commit, a deliberate-red pull request closed unmerged with its CI run, or a mutant id with the main Mutation run whose report records the claimed test in its `killedBy` (or, with no `killedBy`, the two runs that show it surviving before the test merged and killed after), without saying `red not shown`? Does a planted violation cited as evidence sit anywhere but the committed test inputs of the detector it is evidence for, or serve as evidence for anything but that detector?
