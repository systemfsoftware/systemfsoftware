applies_when:
  - a PR body, plan, verification section, review receipt, commit message or solution doc says a new or changed test or check goes red, fails, is falsified, catches a sabotage or was probed
  - a claim of red rests on a hand edit to product code, a test, config or a dependency, or a value planted in a module, config or build output the package ships or installs, in the checkout or a scratch copy anywhere, reverted or not

CONST-T3 asks that every test be able to fail when the behaviour it names breaks (`CONSTITUTION.md:90-95`). A claim that a test or a check can fail is evidence, and a reviewer has to be able to check it. A red the author saw after editing the code by hand, in the working tree, a scratch copy or a scratch clone, and then reverting, cannot be checked: nobody else can open the tree it ran on, and the author chose the edit. Breaking the code while writing a test is still a sound way for the author to learn whether the test can fail. Seemann's advice is to run each new test "and see it fail" ("Tautological assertion", https://blog.ploeh.dk/2019/10/14/tautological-assertion/). That is a working aid, not evidence for anyone else. Mutation never runs locally (root `AGENTS.md` REPO-D3, `AGENTS.md:68`) and runs in CI only on main (`compound-packs/ci-wall-clock/mutation-runs-nightly-on-main.md`). `compound-packs/schema-laws/refusal-properties-cover-unobservable-boundaries.md:41` lists can-fail routes for a refusal property; where the two differ, this rule governs, and `:41` is re-pointed here once #769, which edits that file, lands.

## Rule

A change that claims a test or check can fail names a red that CI observed on a commit a reviewer can open, through one of three routes or, for a detector, its committed planted fixture (below), or it states exactly `red not shown` (capitalised only at the start of a sentence). In every route, the red is the claimed test or check failing, not another test of the same behaviour:

1. **The claimed test red over the real, unmodified pre-fix code in CI.** The claimed test is added on its own over the pre-fix code, with no other edit, and CI runs it there and one of its own assertions fails. A red from failing to load, resolve or type-check, or from the CI run itself, is not this route; where the subject does not exist before the fix, route 1 is unavailable and route 2 applies. Once the change's branch carries the fix, the test-only commit goes on a throwaway branch with a pull request against `main`, closed unmerged. The claim names that commit and the CI run id, and that run finishes before the fix is pushed, since in this repository the next push to the branch cancels it (`.github/workflows/ci.yml:10-12`), and so does the conflict watcher when the pull request turns dirty (`:33-46`). A generated-input property run that failed in CI on unmodified code is this route.
2. **A deliberate-red throwaway CI pull request.** A draft pull request against `main`, from a branch that starts at the head of the change under review and so carries the claimed test (in this repository a pull request's CI runs only when it targets `main`, `.github/workflows/ci.yml:6-7`), breaks the code holding the behaviour, or for a gate adds one input that violates it, and changes nothing else. One such pull request may carry several claimed tests and their breaks only when the claim names, for each claimed test, its failing test id in that run. Its commit is never pushed to the change's own branch, so the real head never moves. The red is one of the claimed test's own assertions failing or, for a gate, the gate reporting that input; a failure to load, resolve or type-check does not count. The claim names the pull request and the id of the CI run in which the claimed test failed, and the pull request is closed unmerged.
3. **The Mutation lane on main**, its nightly run (the schedule lands with #733; until then, a dispatch) or a dispatch of that lane on main, named by the mutant id, the run id, and the test id that run's report records in the mutant's `killedBy` (the runner names a test `<file>#<test name>`). A report part rebuilt from a shard's event stream records no `killedBy`. Two runs, one before the test merged showing the mutant surviving and one after showing it killed, are not this route: any other merge between them, a caller of the mutated code included, can account for the kill. For such a mutant, the claim cites a later dispatch whose report records the `killedBy`, or states `red not shown`. The report artifact is kept for 14 days (`.github/workflows/reusable-mutation.yml:394`), so the route holds only while the report a reviewer would open still exists. It exists only for a test already on main and a file the lane mutates (today, the workflow files the planner admits).

A red is evidence for the claimed test as it stood in that run: when the test changes after the run, the claim cites a newer run or states `red not shown`.

When no route applies, the change states exactly `red not shown` and names, for each route, why it could not be produced, citing a run id, report or commit a reviewer can open that shows the route attempted or unavailable. The review then weighs the test without that evidence. `red not shown` discloses missing evidence and never waives CONST-T3; stating it when a red was observed, or with a route's reason missing or contradicted, is a finding.

- **No local probe as evidence.** A hand edit to product code, a test, config or a dependency, made in the checkout or in a scratch copy or clone anywhere, `/tmp` included, is never evidence that a test or check can fail, and citing one is a finding. A mutant applied by hand, a local edit and revert, a value planted in a module, config or build output the package ships or installs, and the pre-fix source swapped in locally are all such edits. That holds whether the edit was reverted, described in the PR body, or carried through review. While working, the author may still break the code to see a test fail; the evidence is the red one of the three routes then shows. A body that mentions such a probe calls it a working aid and gives a route or `red not shown` beside it. When a probe ran and is no longer cited, the body says that it ran and is withdrawn as evidence; it neither deletes the mention without a word nor states that no probe ran. The inversion loop in `docs/solutions/architecture-patterns/extraction-strands-the-origins-gate.md:63-70` (inject a negated predicate, observe red, restore) is that working aid; pushed as a deliberate-red pull request, its red is route 2. A gate, rule, plan or solution doc that a change adds or edits and that asks for can-fail evidence names one of the three routes, or cites this rule for them, or, for a detector, its committed planted fixture. A dated plan nobody edits stays as the record it is.
- **A detector's planted fixture is a test input, not a mutant.** A lint rule, gate or guard is shipped code whose behaviour is to report a violation, so its test feeds it one: a `RuleTester` invalid case, a known-bad file in its fixture folder, a `--selftest` case whose input sits in that folder. A CI step that commits a scripted violation into its own throwaway checkout, runs only that detector over it, and resets the checkout before anything else runs is the same kind of input: the plant's text is committed in the workflow, and no product run sees it (`compound-packs/ci-wall-clock/no-lane-grades-the-repos-own-docs.md:42-59`). Such a planted violation is can-fail evidence for that detector's own logic alone, never that the governed tree's config runs the detector (a run of the shipped tool over the tree as configured, such as that CI step, shows that), and only when all of these hold. It is committed in the change, and CI runs the detector's test over it. It lives in that test's own inputs, the test file, a fixture folder under the test tree or the CI step's own script, never in a module, config, build output, lockfile, patch or dependency that the product ships or installs. It is read only when the detector's test runs, never by the product's own runs. It violates the detector in the idiom the governed tree uses, not only in the idiom the detector's tests are written in (`docs/solutions/architecture-patterns/dynamic-import-blinds-static-provenance-rules.md:61-63`). The claim names the fixture path and the CI run. It shows nothing about whether any other test can fail. A product test run against an edited copy of product code is a mutant whatever folder holds the copy, and so is an edit to the detector itself, such as a deleted branch or a weakened pattern: its red goes through route 2.
- **The vendored constitution says otherwise until upstream changes.** Its CONST-T10 criterion "Sabotage after green: break one core law and one published field; at least one test goes red" (`repos/constitution/ENFORCEMENT.md:214`) prescribes the hand-applied route. That file is read-only here (root `AGENTS.md` REPO-S3). systemfsoftware/constitution #31, open, replaces that check, as this repository decided (`docs/plans/2026-10-13-0612-refactor-retire-generated-schema-laws-plan.md:147`): its refusal criterion names can-fail evidence by run or mutant id, through the routes above, and carries the per-route `red not shown` duty this rule adopts. Until #31 merges and the vendored copy is updated, this rule governs changes in this repository, and a change the vendored check reaches that offers a route instead of that sabotage declares the breach in its body, naming CONST-T10 and the case, as the law's waiver requires (`repos/constitution/ENFORCEMENT.md:217`).

```text
# WRONG: systemfsoftware/systemfsoftware #56 body (merged 5645a62eed, 2026-08-05)
In place of a Stryker run, each of the seven kernel mutants below was applied by hand and the suite re-run:
killed  maxDepth 2 -> 3 (cap raised)              -> ∀e_ExprNesting_≤DepthCap

# RIGHT: neutral shape, no citation
Can fail: test-only commit <sha> adds ∀e_ExprNesting_≤DepthCap over the unmodified pre-fix code; it failed in CI run <run id>.
Can fail: draft pull request #<n> raises the cap to 3 and nothing else; ∀e_ExprNesting_≤DepthCap failed in CI run <run id>, and the pull request was closed unmerged.
Can fail: the rule's test reports the committed fixture tests/fixtures/planted-effect.tsx in CI run <run id>.
```

Incidents. Pull request bodies in this organisation have offered a local probe as the evidence that a test or check can fail, and kept it through review rounds. In systemfsoftware/systemfsoftware, #56 (`5645a62eed`, 2026-08-05) offered seven kernel mutants applied by hand in place of a Stryker run. #761 (`0923912eed`, 2026-10-13) deleted a pack gate that asked a reviewer to "check it by widening the refinement locally once" (`5965b034b5:compound-packs/schema-laws/refusals-beside-generated-laws.md:52`), because widening by hand is a hand-applied mutant (`docs/plans/2026-10-13-0612-refactor-retire-generated-schema-laws-plan.md:135`). Within two days in October, four more bodies did the same. systemfsoftware/gritlint #20 (2026-10-12) cited line edits in a scratch copy as red probes. systemfsoftware/systemfsoftware #763 (2026-10-13) cited a removed release call as the failing scenario. systemfsoftware/pnpm-release-management #64 (2026-10-13) cited a mutant in a scratch clone as "falsification". systemfsoftware/systemfsoftware #737 (2026-10-13) cited a planted invalid option and a case arm deleted in a scratch copy. Three of the four bodies withdrew the probe before merge. A fifth, systemfsoftware/systemfsoftware #771 (2026-10-13), said its examples typecheck "and a planted typo fails the same check"; fourteen minutes before merge the sentence became "Red not shown", with no word that a typo had been planted. On the same day, in a private repository, at least three pull requests from two sessions offered a sabotage of the code under test, each restored, as the evidence that a new scenario or law goes red. Two of the four scenarios were then shown red through the routes above: systemfsoftware/pnpm-release-management #64 cites a CI run of its test over the unmodified pre-fix code, and #763's scenario failed in the deliberate-red pull request systemfsoftware/systemfsoftware #764, closed unmerged.

Gate: `review` — Does the diff, its plan, its PR body, a verification section, a review receipt, a commit message or a solution doc it adds or changes claim that a test or check can fail on the strength of a hand edit to product code, a test, config or a dependency, a mutant applied by hand, a local edit and revert, a scratch copy or clone, a value planted in a module, config or build output the package ships or installs, or the pre-fix source swapped in locally? Does a gate, rule, plan or solution doc the diff adds or changes prescribe editing code by hand to show a red as evidence, or without naming beside it one of the three routes, a detector's committed planted fixture or `red not shown`? Does a can-fail claim lack a CI run in which an assertion of the claimed test failed over the unmodified pre-fix commit, a deliberate-red pull request closed unmerged with its CI run, a committed planted fixture in a detector's own test inputs with the CI run of that test, or a mutant id with the main Mutation run whose report records the claimed test in its `killedBy` without saying `red not shown`? Does a `red not shown` lack, for any route, a reason with a run, report or commit a reviewer can open, or stand where a red was observed? Does a change the vendored CONST-T10 check reaches offer a route instead of its sabotage without declaring the breach? Does a body drop a probe it ran without saying that it ran and is withdrawn, or state that no probe ran when one did? Does a planted violation cited as evidence sit anywhere but the committed test inputs of the detector it is evidence for, or serve as evidence for anything but that detector? Is it read by the product's own runs, or written in an idiom the governed tree does not use?
