# UI State Compound Pack

Components render and dispatch only. How a React application holds state: server data lives in effect-atom atoms over Effect services, a component performs no I/O and React code runs no React Effect, every Effect the UI runs is an atom of one runtime built from a Layer, and display derivation is a named pure function. The pack governs application UI, meaning the components, hooks and view-models of an app or UI package. Four of its rules do not govern the implementation of the effect-atom bindings (`packages/atom/effect-atom`, `packages/atom/effect-atom-react`), which are the runtime edge: `useAtomValue`'s own inline `Atom.map` (`packages/atom/effect-atom-react/src/hooks-value.ts`) is not a `view-models-are-pure-functions` finding. `react-runs-no-effect` governs `packages/atom/effect-atom-react` as it governs every other React code, with no exception.

Rules:

- `server-data-lives-in-atoms`: data from a server, an Effect service or another component is read through atoms, never copied into `useState`, `useReducer` or `useRef`, and no module imports a React server-state library. Incidents a, b and c (2026-10-11); incident g (2026-10-11) is the UI-local `useState` the rule allows.
- `components-perform-no-io`: a `.tsx` module performs no I/O and names no I/O global, clock or timer. Incidents b, e and f (2026-10-11).
- `components-dispatch-to-runtime-atoms`: every Effect the UI runs is a runtime atom of one runtime built at module scope; an event handler dispatches at most one command. Incidents c and d (2026-10-11).
- `view-models-are-pure-functions`: sorting, filtering, grouping, formatting and status-to-label mapping are named pure functions in a `.ts` module, applied as `useAtomValue(atom, f)`. Incident h (2026-10-11).
- `react-runs-no-effect`: React code runs no `useEffect`, `useLayoutEffect`, `useInsertionEffect` or `useEffectEvent` from `react` and imports `react` by name, with no exception; binding code subscribes through `useSyncExternalStore`, and the code that mounts the app restores saved state before the first render. Incidents b, c, e and f (2026-10-11) and the ruling of 2026-10-13.

Three rules are partly mechanized in `@systemfsoftware/oxlint-config-recommended`: `no-restricted-imports` for the server-state libraries, `no-restricted-globals` and `no-restricted-properties` for `fetch` in `**/*.tsx`, and, for `react-runs-no-effect`, `no-restricted-imports` on `react` beside effect-platform's `no-react-effect`. The preset also enables the oxlint React plugin: every `correctness` rule at error, the React Compiler checks included, except `react/rules-of-hooks`, which decides what is a hook from its name alone and so reports Effect's `Service.use(...)`; `react/hooks` checks the Rules of Hooks inside components and hooks instead. `react/capitalized-calls`, `react/rule-suppression`, `react/unsupported-syntax`, `react/no-unstable-nested-components`, `react/no-array-index-key`, `react/no-clone-element`, `react/no-react-children` and `react/prefer-function-component` are errors too. "Only call Hooks from React functions" stays review-owned. Each lint is narrower than its rule, and review covers the rest. No lint tells server data from UI-local `useState`, so none exists. Under `src/`, the preset's `effecttsgo/global-date` already reports `new Date(x)`, `new Date()` and `Date.now()`, `effecttsgo/global-timers` reports `setTimeout` and `setInterval`, and effect-platform's `no-unported-time-source` reports `performance.now()`, in `.tsx` as in `.ts`.
