# Composition Compound Pack

How the units of a TypeScript monorepo compose instead of collapsing into each other. It covers which kinds of unit exist, which may depend on which, where tests reach code, where configuration and Layers are bound, and how a template leaves the monorepo. `package-topology` governs one published package's surface. This pack governs the graph of units and the applications at its edges.

Every rule names a mechanical gate. A rule that only review enforces does not hold: in younna-ai, review let a Cloudflare Worker publish 136 subpath exports, most of them internals exposed so tests could import them.

Rules:

- `three-unit-kinds`: every workspace unit declares itself a library, an application, or a template, and each kind has a fixed manifest shape.
- `dependency-direction`: edges point from applications to libraries and from libraries to lower libraries; nothing imports an application, and the graph has no cycles.
- `applications-export-nothing`: an application's manifest has no `exports`; what two applications share lives in a library both depend on.
- `core-and-adapters`: runtime- and framework-neutral code lives in a core library; each runtime or framework gets an adapter library; runtime choice is an export condition, never a deep path.
- `role-entries-only`: a private library exports `.` only, one `mod.ts` namespace barrel; runtimes are conditions, drivers and framework bindings are their own libraries, and nothing is exported for tests.
- `tests-stay-home`: tests live in their package's `tests/` and import every package, their own included, only through its public specifier; nothing is exported so a test can reach it.
- `source-condition-resolution`: workspace packages resolve to source through a custom export condition, so neither development nor tests need a build or a deep import.
- `config-at-the-edge`: only applications read configuration and choose Layers; libraries take their dependencies as services.
- `contracts-between-applications`: two applications that talk share a contracts library (schemas, RPC groups); neither imports the other.
- `templates-leave-the-monorepo`: a template builds, tests and deploys after being copied out alone, with published dependencies and no monorepo tooling.
- `split-by-consumer-merge-by-co-change`: split a library when its consumers use disjoint halves or different runtimes; merge two that always change together; no library with one consumer and no reuse.
- `unpublished-surfaces-are-free`: an unpublished workspace library has no versioned surface, so a wrong shape is deleted and rebuilt rather than kept alive for compatibility.

Evidence base (source trees read 2026-10-21): TanStack Router and Query (`query-core` has no dependencies or peers; router-core adds only runtime entries; runtimes are export conditions), Vitest (role entries plus an explicit `./internal/*`; the `__vitest_source__` custom condition; internal `@vitest/*` packages bundled into `vitest`), Deno std (a package per module; `_tools/check_mod_exports.ts`; `_` prefix for private files; `unstable_` tier), Effect 4 (`effect-smol`: one namespace barrel; `./internal/*: null` plus a lint rule; services in core and implementations in runtime packages), Rat Stack (layers carry their cloud resources; removal checklists; the fence), and nythrox/Stead (a shell, a desktop and apps that compose through manifests, not imports).

Service and Layer placement inside a library is governed by `cell-architecture/service-and-layer-boundaries.md`, the barrel shape by `cell-architecture/single-namespace-barrel.md`, and a published package's surface by `package-topology`.

Gates: implemented as subcommands of this repository's `repo-checks` app (`scripts/tools/repo-checks/composition*.ts`), so any enrolled repository runs the same check from its root: `nix run github:systemfsoftware/systemfsoftware#repo-checks -- composition-unit-kinds composition-graph composition-entries composition-imports composition-contracts composition-core-adapters composition-granularity`. Exit 0 holds, 1 a violation, 2 undecided. A unit that has not yet declared its kind is judged as a library, so the cap and the core and environment rules apply before the declarations land. The `template-isolation` gate is a CI job each repository adds for its templates.

How a gate decides. A rule is gated by facts or by a calibrated judge, never by a pattern over source text.

- Fact-gated rules read objective facts from the real tools: the TypeScript compiler (a program per unit built from the unit's own tsconfig and its `moduleResolution`, import and export declarations, type-only imports told apart by `isTypeOnly`), a package.json `exports` resolver that follows conditions and `*` patterns, and the syntax tree with the type checker. Environment access is a type the compiler resolves to Cloudflare's `Env` or to an object with Cloudflare's binding classes, or `process.env`, `Deno.env` and `import.meta.env` followed through aliases, namespace imports and named imports of `node:process`. A reference to effect's `Layer` module is a symbol resolved through the alias chain (renames, destructuring, bare references, barrels, `export *`), and falls back to the module an import names only when `effect` is not installed. An import inside a string or comment is not an import, and a `dist` target is build output the compiler never mistakes for source. A fact must entail the violation to fail: a parameter named `env` whose type is unresolved is not flagged by its name (the check reports the libraries whose dependencies are not installed instead), and a runtime dependency declared and never imported fails only a unit that declares itself a library.
- Judge-gated rules are judgement calls: whether an entry is a role or a folder mirror, whether an export only tests use is legitimate, whether a library should split or merge, whether a core/adapter split is right. The compiler facts become structured evidence (facts are code, injected into the judge's input) and a per-rule rubric (one criterion per line, edge cases written out) goes to a panel of two models over OpenRouter. Each answers evidence first: the facts it cites, then `holds`, `violated` or `uncertain`, then a confidence. `violated` and `holds` need both members to agree; a disagreement is `uncertain`. `uncertain` never fails CI; it is reported for a human. Without `OPENROUTER_API_KEY` the judged rules report their candidates and do not judge. The number of role entries is such evidence (a guide of 8, reported when exceeded), not a limit.
- A judged rule may fail CI only while its calibration kappa is at least 0.7 for the current rubric, panel and evidence shape (`calibration/kappas.json` carries a fingerprint of all three; a changed rubric, panel or evidence field makes the calibration stale, and a stale rule only reports).

Judging the judge. `scripts/tools/repo-checks/calibration/cases.jsonl` holds 121 labelled cases (29 `entries-are-roles`, 37 `test-only-exports`, 32 `granularity`, 23 `core-adapter-split`), each a real unit from a real repository with the evidence the current fact extractor produced for it (`scripts/tools/repo-checks/composition-cases.ts <checkout>` prints that evidence for any checkout; the cases were extracted from these pinned commits): younna-ai at `51fef9b6a3` and `10d7ce6c0e` (including its 136-entry `workers/platform`), TanStack query and router, Vitest, effect-smol, rat-stack, tRPC, Jotai, Astro, the identity-backend-community monorepo (private `./testing` roles) and this repository. A test fails when the field paths the extractor emits differ from the ones the cases carry, and the calibration fingerprint includes that shape, so the frozen evidence cannot drift from the extractor unnoticed.

What the set is made of, and what it is not:

- The labels are the author's, written from the pack's rules. Every case is also rated blind by a second model (`calibration/second-rater.jsonl`, `google/gemini-3.7-flash` reading only the pack's rule text and the facts, never the labels or the rubric). Where the two raters disagree the gold label is `uncertain`: no one is sure, so a human decides and CI does not fail. Author against second rater, Cohen's kappa: `entries-are-roles` 0.51, `test-only-exports` 0.73, `granularity` 0.77, `core-adapter-split` 0.36. There is no human adjudication; the second rater is a model from the panel's vendor family, so this lowers the same-author risk without removing it.
- The set no longer separates by one field. Test-only `holds` cases include private non-root entries (`./testing` roles of `@identity-backend/app-attest` and `android-attest`) and `violated` ones include published packages (Astro's `./_internal/logger`, `./assets/utils/inferRemoteSize.js`); granularity `holds` cases include private tools with no dependents (a `bin`, run scripts, a package with no source) and `violated` ones include published libraries that change together; entries `holds` cases include private libraries and `violated` ones a published package (Astro, 63 entries mirroring its folders). A test fails if a cut by `published`, root or dependent count splits the labels again. `core-adapter-split` has no published violation among the repositories read and stays report-only.
- The rubrics were refined against this set (granularity gained the `bin`, deploy and run-script facts after the false positives in younna-ai's tooling units; test-only gained the asset and `internal` criteria), so the kappas below are in-sample for those refinements. The younna-ai proof re-flags units that are labelled cases (`@younna/agent` `./markets` and `./news`, `@younna/platform` `./vault/laws`), so it is in-sample too; the units it newly judges are the held-out view.
- The panel is nondeterministic across recordings: the same `entries-are-roles` rubric measured 0.68 and then 0.74 in two recordings. A kappa near 0.7 is a coin flip, and a re-recording can move a rule across the gate; `composition-calibrate --record --write` is the only way a gate opens.

`repo-checks composition-calibrate` replays the recorded model answers (`calibration/recorded.jsonl`, the real responses of the panel) and reports agreement as Cohen's kappa per rule over the labels holds, violated and uncertain; `--live` asks the models again, `--record` also re-records them, `--write` also writes `calibration/kappas.json`.
