# A cached pass outlived the toolchain that earned it and surfaced as a false API change

## Problem

`pnpm check` went red on `@systemfsoftware/effect-daemon-spec#api:check` with an api-extractor report mismatch, and nobody had changed the API.

The committed report `packages/effect-daemon-spec/etc/effect-daemon-spec.api.md` had been generated by an older toolchain, and the current toolchain emits a representationally different report for the identical export set. The drift stayed invisible because the package's `build` and `api:check` tasks were cache hits — turbo restored their pass verdicts without re-running anything. An unrelated manifest edit moved the task key, both tasks re-ran under the current toolchain, and the latent mismatch surfaced as a red gate whose error message named the wrong cause.

The general lesson: **a cached pass can outlive the toolchain that earned it.** The toolchain version is not part of the task key, so a stored verdict stays valid by the key's reckoning while the tool that produced it moves on. Any task that regenerates an artifact and compares it against a committed copy carries this exposure.

## Symptoms

The failing task emitted api-extractor's report-mismatch message, which is unconditional on any mismatch (`Extractor.js:202-205` in the installed api-extractor 7.58.9):

```
You have changed the API signature for this project. Please copy the file
"temp/effect-daemon-spec.api.md" to "etc/effect-daemon-spec.api.md", or perform
a local build (which does this automatically).
```

The diff behind the message was representational. Inlined signatures became `typeof` aliases:

```diff
-    readonly poll: <A, E, R, L extends LockConfig>(opts: PollOpts<A, E, R, L>) => Worker_2<E, R, L>;
+    readonly poll: typeof poll;
```

Double quotes became single:

```diff
-            mode: "none";
+            mode: 'none';
```

The preconditions for invisibility: `build` and `api:check` are both cached by default — neither carries `cache: false` (`turbo.json:7-26`, `turbo.json:145-163`) — and the report's input `dist/index.d.ts` is itself a gitignored build output that the cache restores along with the pass verdict.

## What Didn't Work

**Suspecting the local edit.** The working tree carried `perf(global): drop dead vite-tsconfig-paths from test configs`, which touched this package's `package.json`. The natural first read is that the edit changed the API. Ruled out by two facts: `git status` showed `packages/effect-daemon-spec/etc/` unmodified with no source file in the package touched, and a manifest edit cannot alter an API — it can only alter a task key.

**Trusting the error message.** api-extractor emits `You have changed the API signature for this project` for _any_ report mismatch, representational or semantic, because the only comparison it performs is byte-for-byte between `temp/` and `etc/`. There is no severity or wording distinction that separates "the API changed" from "the report format changed". The message names the wrong cause with full confidence, and believing it leads either to hunting a nonexistent API change or to regenerating away a real one.

**Eyeballing the diff.** Tempting, and not robust. The regenerated report also gained an analysis-warnings block that the committed copy lacked:

```
// Warnings were encountered during analysis:
//
// dist/index.d.ts:334:3 - (ae-forgotten-export) The symbol "dynamic$1" needs to be exported by the entry point index.d.ts
```

So "representational" did not mean "whitespace only". A scan for formatting-looking changes can miss content that a mechanical comparison catches.

The discriminator that worked was an **export-set comparison** — sort the lines matching `^export (declare )?(const|function|class|interface|type|namespace)` from both reports and diff them. The sets were identical, which is what proved no API had moved.

## Solution

Regenerate with the current toolchain and commit the result. `api:update` runs api-extractor in `--local` mode, which overwrites the committed copy rather than failing:

```json
"api:check": "api-extractor run",
"api:update": "api-extractor run --local",
```

Landed as commit subject `chore(effect-daemon-spec): refresh the stale api report`. Verified: `api-extractor run` (the non-local `api:check` path) now exits 0 with `API Extractor completed successfully`.

This is a symptom fix. It restores the invariant the gate enforces — committed report equals current toolchain output — and holds until the next toolchain move re-stales it.

## Why This Works

**The report is a derived artifact of a two-stage toolchain.** tsdown emits `dist/index.d.ts`; api-extractor analyzes that file per `mainEntryPointFilePath` (`api-extractor.json:4`) and compares its output against the committed copy in `etc/`. The report's content is therefore a function of tsdown's d.ts emission _and_ api-extractor's report formatting — two independently versioned tools.

**The task key hashes inputs, environment, and dependency hashes, but never the binaries.** `build` hashes `src/**`, the tsconfigs, `package.json`, `tsdown.config.*`, `api-extractor.json`, and `etc/*.api.md` (`turbo.json:9-18`). `api:check` hashes `src/**`, the api-extractor configs, the build tsconfigs, and `etc/*.api.md` (`turbo.json:147-154`), inheriting the build hash through `dependsOn` (`turbo.json:160-162`). The only `globalDependency` is `scripts/patch-tsgo-if-needed.mjs` (`turbo.json:3-4`), which guards the compiler-_selecting script_ rather than the resolved toolchain versions. Nothing in any key is the version of tsdown, api-extractor, or its bundled TypeScript.

**The toolchain did move.** api-extractor held at 7.58.9 throughout, but tsdown moved from 0.22.9 to 0.22.14 in commit subject `build(deps): update tsdown to 0.22.14` — six days after the report was committed and one day before the failure. The d.ts representation the report records changed with the emitting toolchain, not with any source change.

**The cache then did exactly what it is designed to do.** `dist/` and `temp/` are both gitignored. Turbo restored the old `dist/index.d.ts` and the old pass verdicts on every run whose key matched. The key's reckoning was correct — none of its declared inputs had changed. The tool that produced the stored artifacts had moved, and the key had no way to know.

**The trigger was the unrelated manifest edit.** Removing a dead devDependency changed `package.json`, which is a `build` input (`turbo.json:14`), so build's hash moved; `api:check` inherits it through `dependsOn`, so its hash moved too. Both re-ran fresh: tsdown 0.22.14 emitted the new d.ts representation, api-extractor wrote the new report to `temp/`, and the byte comparison against the stale committed copy failed.

One nuance is left honestly unresolved. [The input-hash doc](../tooling-decisions/turbo-cache-requires-complete-input-hash.md) asserts the task key includes the lockfile. The lockfile churned substantially between the report's commit and the incident, including the tsdown move, yet the drift did not surface until the manifest edit. Whether turbo does not hash the lockfile for these tasks, or simply no fresh run happened in that window, is not settled here. The lesson is the same either way: nothing in the key distinguished the binary that produced the stored verdict.

## Prevention

The exposed class is **a cached task that regenerates an artifact and compares it against a committed copy, with the regenerator's version outside the task key.**

Detection before failure is impossible in-band by construction: the cache is the detector's blind spot, because a hit restores the stored verdict without ever running the comparison. Drift surfaces only when the key moves for an unrelated reason (accidental detection, as here) or when the key is made to move as the toolchain moves (the fix). Out-of-band, any fresh-cache environment catches it on first run.

### The repo's real instances

1. **api-extractor reports** — 40 committed `packages/**/etc/*.api.md` files across 34 packages, each with two cached executions: the standalone `api:check` task and the check embedded in every package's `build` script (`"build": "tsdown && pnpm api:check"`). One member failed; the other 39 share the exposure identically. This is the class's home. Most packages commit one report; three commit several (`effect-daemon-spec` five, `stryker-plugins` and `effect-schema-extensions` two each), because a package that publishes multiple entry subpaths gets one report per entry — so the file count moves independently of the package count whenever an entry set is re-chunked. The embedded copy also distorts the failure count: because a stale report fails `build` rather than the report step, one stale report can surface as several red tasks, and a later regeneration commit on this branch recorded the gate naming seven failures for four causes. Count causes, not failures.
2. **A report with no checking task at all** — `packages/effect-gherkin-spec` commits an `etc/*.api.md` report but declares no `api:check` script, so `turbo api:check` skips it and its `build` script never invokes one. This is the same artifact class as instance 1 with _zero_ executions rather than two: no cache is involved, so none of the mechanisable options below apply to it, and the report can drift from the moment it is written with nothing that could ever go red. Strictly worse than a stale hit, and invisible for the opposite reason — not a restored verdict, but no verdict.
3. **Stryker incremental report** — the gitignored `packages/*/reports/stryker-incremental.json` is an input to the cached `mutation` task. Adjacent rather than identical: the cache restores a stored mutation verdict across a toolchain drift, and with no committed copy there is nothing to go red, so stale verdicts are reused silently instead of failing loudly. Same mechanism, worse failure mode.
4. **Absent classes, stated plainly** — no committed Vitest snapshots and no `toMatchSnapshot`/`toMatchInlineSnapshot` calls anywhere under `packages/`. The snapshot-test instance of this class does not exist here.
5. **Borderline non-instances** — `//#check:exports` compares regenerated `dist/` against `package.json` exports, but its comparison target is itself a hashed input, so a toolchain change cannot silently flip the verdict. `attw` validates the packed tarball with no committed copy. Neither is in the class.

### Mechanisable options, with tradeoffs

**Pin the toolchain into the key (recommended).** Add `"$TURBO_ROOT$/pnpm-lock.yaml"` to `api:check`'s `inputs`. The lockfile is the resolved-version manifest, and a lockfile change is exactly the event at which these binaries can move. Tradeoff: every dependency bump anywhere invalidates all 40 comparisons. That cost is semantically correct — a lockfile change _can_ change any report — and each comparison is a short api-extractor pass that turbo parallelizes. Residual gap: the check embedded in each `build` script still rides the cached build task, so either add the lockfile to `build`'s inputs too, or drop the redundant `&& pnpm api:check` since the standalone task already depends on build and is gated in `check:ci`. Note this option does nothing for instance 2, which has no task to add inputs to — that one needs an `api:check` script before any key-completion move can reach it.

**Periodic forced regeneration.** A scheduled uncached job running `api:update` across packages, then `git diff --exit-code -- 'packages/**/etc/*.api.md'`. Fails whenever today's toolchain would rewrite a committed report. It must run uncached or it inherits the blindness. Tradeoff: needs scheduled-runner infrastructure, and the staleness window equals the schedule period. A detector, not a fix — a complement rather than a substitute. Use `**`, not `*`: 24 of the 40 reports live in nested package directories (`packages/oxlint-plugins/*`, `packages/stryker-js/*`), so the single-star glob silently covers 40% of the class and reports success for the rest — this doc's own failure mode wearing a different hat.

**Never cache the comparison.** `"cache": false` on `api:check` (precedents exist in this repo: `test:contract`, `//#format:check`, `clean`). Removes the exposure at its source, but re-analyzes every package on every run and still misses the build-embedded check. Costs more than the lockfile pin for the same guarantee.

### Diagnostic guardrail — works today, zero infrastructure

When `api:check` goes red, run the export-set comparison **before** touching anything:

```bash
PKG=packages/effect-daemon-spec
diff <(git show HEAD:$PKG/etc/effect-daemon-spec.api.md \
        | grep -E '^export (declare )?(const|function|class|interface|type|namespace)' | sort) \
     <(grep -E '^export (declare )?(const|function|class|interface|type|namespace)' \
        $PKG/temp/effect-daemon-spec.api.md | sort)
```

An empty diff means the change is representational — regenerate with `api:update` and read the resulting diff. A non-empty diff means a real API change — fix the API, do not regenerate. This guards both directions: believing the misleading message, and `api:update`-ing away a genuine change.

**Bottom line.** Some key-breadth cost is unavoidable, because the drift is invisible by construction and the only free detection is an accidental key move. The lockfile pin is the cheapest correct fix; the export-set comparison is the diagnostic discipline that costs nothing.
