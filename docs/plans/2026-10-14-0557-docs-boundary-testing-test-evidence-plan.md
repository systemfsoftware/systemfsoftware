# Can-fail evidence and shipped test subjects - Plan

## Goal Capsule

- **Objective:** `boundary-testing` judges two kinds of test evidence that no rule judges today. A claim that a test or check can fail names a red CI observed through one of three routes, or states `red not shown`, and never rests on a mutant applied by hand or a local edit-and-revert probe; a detector's committed planted fixture counts for that detector alone. A test's subject is code the package ships, never a function, table or literal the test file declares.
- **Means:** two new rules, `can-fail-evidence-is-an-observed-red` (R1-R3) and `the-subject-is-shipped-code` (R4-R6), indexed in the pack README (R7).
- **Product authority:** the root's intent of 2026-10-13, items (4) and (6), and the root's addition of 2026-10-14 developing item (4): its four incident candidates, its evidence routes (the unmodified pre-fix commit in CI, a deliberate-red throwaway CI pull request, the nightly lane on main, or `red not shown`), and the lint-fixture question; and the brief redelivered on 2026-10-14, which adds the can-fail vocabulary, the hand edit to tests, config and dependencies, withdrawn probes stated rather than denied, the exact phrase `red not shown`, #771 and an unnamed private pattern as incidents, constitution #31, and placement tested against every enrolled repository. The root's `boundary-testing` placement and cross-links were hypotheses; this plan tests them. It settles the rule ids, the scope, the carve-out boundary and the lint hypothesis; the carve-out stays open to review.
- **Stop conditions:** stop and report before editing `repos/` (REPO-S3), before running any mutation (REPO-D3), and before adding a lint rule, lane or CI job (GATE1).

## Product Contract

### Summary

Two new `boundary-testing` rules. One governs what counts as evidence that a test can fail. The other governs what a test may take as its subject. The intent's item (5) and item (7) go elsewhere (Scope Boundaries).

### Key Decisions

- **Two rules in `boundary-testing`, not amendments.** Both rules govern what a test may claim as evidence and what it may take as its subject. That is test verification, the remit `boundary-testing` already holds for oracles and parity. The oracle rule's subject is the expected value, and both new subjects differ from it. Their ids are `boundary-testing/can-fail-evidence-is-an-observed-red` and `boundary-testing/the-subject-is-shipped-code`. Placement was tested against enrolment, not assumed: each of the nine repositories that enrol packs from this one selects `boundary-testing` (this repository, systemfsoftware/stryker-js-effect, gritlint, pnpm-release-management and api-extractor-effect by name, are-the-types-wrong-effect by taking every pack, and three private repositories by name), while `mutation-discipline` is absent from api-extractor-effect (`942ac814e7:.compound-engineering/config.yaml:5`) and from one private repository. A rule in `mutation-discipline` would not load in those reviews. Each repository loads the rules once it repins to a commit that carries them; the repins are their own changes.
- **Three routes, each a red CI observed on a commit a reviewer can open.** The routes are the root's: the claimed test over the unmodified pre-fix commit in CI, a deliberate-red throwaway pull request closed unmerged, and the Mutation lane on main; otherwise `red not shown`. The earlier separate route for a failed generated-input property run is folded into the first, because such a run is a red on unmodified code. The earlier alternative "a pushed commit holding the new test over the pre-fix code, with the command and the failing output" is dropped: it accepted a locally reported red, and gritlint #20's replacement evidence (the pre-fix binary run locally) shows that shape. Mutation evidence stays main-only (REPO-D3).
- **A detector's planted fixture is a test input, with a boundary.** A lint rule, gate or guard reports violations, so its test must feed it one, and a committed known-bad fixture is how this repository already proves a gate (Ownership). The carve-out holds only when the plant is committed, CI runs the detector's test over it, it lives in that test's own inputs and never in a module, config, build output, lockfile, patch or dependency the product ships or installs, only the detector's test reads it, and the claim names it and the CI run. It is evidence for that detector alone. A product test run against an edited copy of product code, or an edit to the detector itself, is a mutant whatever folder holds it, so the carve-out cannot carry a product-code or dependency mutation. #763 shows both sides: "a planted `useEffect` in `src/`" (a plant in shipped code, refused) and `856efddae3`, "a planted fixture pins it" (a committed detector input, allowed).
- **Item (4) stays with item (6) in one PR; item (5) does not.** Both rules judge test evidence in `boundary-testing` and share this plan and its review. Item (5) changes a published plugin's message and needs a changeset, and #769 edits the same plugin's README, so it stays a separate pull request.
- **Enforcement stays `review`.** A PR body is prose. A CI check that greps bodies for probe words would be a new gate, which needs the operator's sign-off (GATE1), and its false-positive class (a body that names a withdrawn probe as a working aid) is a sanctioned shape here.
- **The structural lint was tested as a hypothesis and is not built.** The hypothesis: a test-discipline oxlint rule could flag a test whose subject its own file declares. A sampled census of test files under `packages/**` at `de684e25d6` (the first 200 the glob returned) found no live instance, and local fixtures, arbitraries and wrappers make up its false-positive classes. The #747 instance sits in `scripts/tools/`, a Deno tree that oxlint does not lint. A new gate needs the operator's sign-off (GATE1) and an earned defect. The gate stays `review`, and the root may revisit the lint with these facts.
- **Item (5) is its own change.** The `tests-import-public-api` fix text (`packages/oxlint-plugin/oxlint-plugin-test-discipline/src/rules/tests-import-public-api.config.ts:5-6`) offers only "public" or "internal". A third branch, never exporting a binding only so a test can reach it, changes a published package's message and needs a changeset. It is a different review from pack text, so it is the next pull request. Item (6) (the #747 contract tests whose oracle is the subject) fits here, as `the-subject-is-shipped-code`. Item (7) and the alignment of `compound-packs/ci-wall-clock/failures-name-the-gate-and-location.md:19` with the rule that no local Stryker command of any kind reproduces a failed Stryker step (the main-only dispatch, or `gh run rerun <run-id> --failed` or `--job <id>`) stay queued.
- **Item (7) gets a solution entry.** Only one short-ref enrolment incident was found (pnpm-release-management#57). Without a second incident, a pack rule is not earned, so a `docs/solutions/` entry records it, in its own change.

### Requirements

- R1. A new rule `compound-packs/boundary-testing/can-fail-evidence-is-an-observed-red.md` in the pack format: frontmatter `title`, `applies_when`, `tags`; the why from the verified public incidents; `## Rule`; WRONG/RIGHT; a closing `Gate: review` question answered from the diff, the PR body and the commit messages. It covers a claim that a test or a check can fail.
- R2. Routes, in each of which the red is the claimed test or check failing: the claimed test added alone over the unmodified pre-fix commit, with one of its own assertions failing in CI (the commit and the CI run id; a red from failing to load, resolve or type-check does not count, and where the subject does not exist before the fix this route is unavailable; a generated-input property run that failed in CI on unmodified code is this route); a deliberate-red throwaway pull request based on the head of the change under review, which carries the claimed test, that breaks only the code holding the behaviour or, for a gate, adds one input that violates it (the red is the claimed test's own assertion failing or, for a gate, the gate reporting that input, never a load, resolve or type-check failure; the pull request and the CI run id, closed unmerged; one such pull request carries several claimed tests only when each one's failing test id in that run is named); a mutant the claimed test kills in the Mutation lane on main, its nightly run or a dispatch of it on main (the mutant id, the run id and the test id the report records in the mutant's `killedBy`; for a report part rebuilt from the event stream, which records no `killedBy`, a later dispatch whose report records it, since two runs bracketing the merge cannot exclude another merge accounting for the kill; only while the 14-day report exists, for a test on main and a file the lane mutates). Otherwise the change says `red not shown`. A red is evidence for the claimed test as it stood in that run: when the test changes after the run, the claim cites a newer run or states `red not shown`.
- R3. A hand edit to product code, a test, config or a dependency, in the checkout or a scratch copy anywhere (`/tmp` included), is never evidence, and citing one is a finding: a hand-applied mutant, a local edit and revert, a value planted in a module, config or build output the package ships or installs, and the pre-fix source swapped in locally, whether reverted, described or carried through review. A body that mentions one calls it a working aid and gives a route or exactly `red not shown` beside it; a probe that ran and is no longer cited is named as run and withdrawn, never denied or dropped without a word. A deliberate-red commit is never pushed to the change's own branch. systemfsoftware/constitution #31 is cited for the `ENFORCEMENT.md:214` conflict. A gate, rule, plan or solution doc that a change adds or edits and that asks for can-fail evidence names one of the three routes; a dated plan nobody edits stays as a record. The inversion loop of `docs/solutions/architecture-patterns/extraction-strands-the-origins-gate.md:63-70` stays a working aid, and its red pushed as a deliberate-red pull request is route 2; that doc's `:70` says so. The rule names the vendored `ENFORCEMENT.md:214` conflict and how it resolves.
- R4. A new rule `compound-packs/boundary-testing/the-subject-is-shipped-code.md` in the same format. The subject a test asserts on is declared in a shipped module, never in a test file or a test-tree helper; a port fake run beside the real adapter by its contract suite is the one test-declared subject. A test file (one the runner collects that ships nothing) imports it through the route the test-placement lint allows (in a tree no such lint covers, from the module that ships it) and declares inputs only (fixtures, arbitraries, builders, fakes); an expected value it writes is an oracle, not a subject. An in-source block in a shipped module may assert on that module's own declarations. A binding a shipped module exports only so a test can reach it does not count as shipped.
- R5. No assertion on the language's, the runtime's or a dependency's semantics as a stand-in for the package. Dependency semantics the package relies on go to `pin-dependency-semantics`, and the reason for a choice goes to the chosen code's doc comment.
- R6. A case table checks a shipped predicate. A table in a test file whose predicate the test file or a test-tree helper declares is deleted with it, or the predicate moves to the module that uses it. An in-source table in a shipped module stays.
- R7. The pack README lists both rules with their slugs, and the subject rule's `applies_when` names each case its Gate asks about, including a binding exported only so a test can reach it.
- R8. The can-fail rule's `applies_when` names a claim ("goes red", "fails", "falsified", "sabotage", "probe") in a PR body, plan, verification section, review receipt, commit message or solution doc, a hand edit as evidence, a withdrawn probe, a prescription, and a planted violation added to a detector's test inputs, so every case its Gate asks about selects the rule.
- R9. A planted violation is can-fail evidence only for the logic of the detector whose committed test inputs hold it, never that the governed tree's config runs it, under the boundary in Key Decisions, read only when that detector's test runs and written in the idiom the governed tree uses; a CI step that commits a scripted violation into its own throwaway checkout, runs only that detector and resets the checkout is the same input (`compound-packs/ci-wall-clock/no-lane-grades-the-repos-own-docs.md:42-59`), so the two packs agree; a product test run against an edited copy of product code, or an edit to the detector itself, is a mutant and goes through route 2.
- R10. The ten solution docs that teach a local probe as proof (`architecture-patterns/extraction-strands-the-origins-gate.md:70`, `build-errors/a-disable-comment-names-the-config-key.md:41`, `build-errors/oxlint-extends-drops-ignore-patterns.md:60`, `architecture-patterns/exported-live-state-is-not-structurally-decidable.md:206-210`, `changeset-gate-enforces-intent-name-liveness.md:95`, `mutation-budgets-split-rule-packages-into-private-cells.md:40`, `build-errors/oxlint-preset-overrides-are-replaced-by-a-spread.md:54`, `architecture-patterns/dynamic-import-blinds-static-provenance-rules.md:61-65`, `architecture-patterns/deleting-a-consumer-leaves-its-requirement-standing.md:132-136` and `architecture-patterns/blueprint-type-index-reads.md:55-57`) say instead that the probe is a working aid and name the evidence a reviewer can check.

### Acceptance Examples

- AE1. **Covers R2, R3.** A PR body says "applied the mutant by hand, the test went red, reverted", or "in a scratch clone, removing the marker fails both rows": refused. It says "test-only commit `<sha>` over the unmodified pre-fix code failed in CI run `<id>`": holds. It says "deliberate-red pull request #<n>, CI run `<id>`, closed unmerged": holds. It says `red not shown`: holds, and the review weighs the test without that evidence.
- AE7. **Covers R9.** A lint rule's test reports the committed fixture `tests/fixtures/planted-effect.tsx` in CI run `<id>`: holds, for that rule. A "fixture" that copies a product module with one line changed, run under the product's own test to show it fails: refused. - AE8. **Covers R3.** A body says "a scratch-copy probe was run as a working aid and is not evidence; red on the unmodified pre-fix commit in CI run `<id>`": holds.
- AE2. **Covers R3.** A pack gate the diff adds reads "check it by breaking the code locally once": refused.
- AE3. **Covers R4, R6.** A test file declares `const isAllowed = (x) => ...` and asserts a case table against it: refused. It imports `isAllowed` through the package's published name, from the module that ships it: holds.
- AE4. **Covers R4.** A test file declares an arbitrary and a fake store, and asserts on a decider it imports: holds, because those declarations are inputs.
- AE5. **Covers R5.** A test asserts `Object.is(NaN, NaN)` to explain a comparison choice: refused. A parity test pins a dependency's parse result that the package relies on: holds under `pin-dependency-semantics`.

- AE9. **Covers R3, R8.** A PR body first says "a planted typo fails the same check" and later reads only "Red not shown": refused, because the probe that ran is dropped without a word. It reads "a planted typo was tried locally and is withdrawn as evidence; red not shown": holds. A body cites a test's assertion edited by hand in `/tmp` and reverted: refused.

### Assumptions challenged (destructive review)

- **"A hand edit is a local mutation run, so REPO-D3 already forbids it."** Broken: REPO-D3 forbids starting local mutation runs, and a one-off manual edit is not a Stryker run.
