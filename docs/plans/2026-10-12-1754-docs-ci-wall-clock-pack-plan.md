# The ci-wall-clock compound pack - Plan

## Goal Capsule

- **Objective:** whoever plans or reviews a CI-facing change in a systemfsoftware repo judges it against one set of wall-clock rules with stable ids. Under those rules a pull request gets a fast verdict on what it affects, every push to main gets its own heavy verdict, and a red main is reverted or fixed the same day.
- **Means:** a new compound pack `compound-packs/ci-wall-clock/` (a README plus twelve rule files) in the format the Compound Engineering Packs guide defines (KTD6), enrolled in this repo's `.compound-engineering/config.yaml` (KD1, KTD1).
- **Authority:** the owner's brief ("this is worthy of a new compound pack. the current long CI mockery we have in all repos is extremely problematic"), the sub-conductor's and root's rulings of 2026-10-11 and the runner root's amendments of 2026-10-12, under `CONSTITUTION.md` and the root `AGENTS.md`. This plan supersedes `docs/plans/2026-10-12-1738-docs-ci-wall-clock-pack-plan.md` (in the chain from `docs/plans/2026-10-11-0610-docs-ci-wall-clock-pack-plan.md`) and carries the full contract with every 2026-10-12 amendment and ruling applied. Each superseded plan was removed from the tree, as REPO-D2 requires, and is readable in this pull request's commits. A separate shared-tooling unit implements these rules in the reusable workflows and cites this pack's ids; it is not active scope here.
- **Stop conditions:** pack text, the config line and this plan only. No edit under `.github/`, no gate or lint rule, no change in any other repo, no repo or org settings change.
- **Execution profile:** docs-only change delivered as one pull request; verification is reading each rule's check question against its own cited lines, the pack loader, the privacy grep and `pnpm check:local`.
- **Finishes and ships:** the ce-work executor opens the PR, runs the full ce-code-review, puts its rulings in the PR body and watches CI to green. The operator merges.
- **Open blockers:** none. The root closed Q5 and Q7 at the plan gate (2026-10-11).
- **Evidence (kept out of the repository):** the brainstorm's notes on measurements, ownership, incidents, prior art, revert credentials, this repo's jobs and claim verdicts, and the org's repository visibility list (`gh repo list systemfsoftware --json name,visibility`). Workflow lines were read with `git show origin/main:<path>` at origin/main `02bf9653b1` unless another SHA is named. The incident notes name private repos and are never quoted from. No rule file cites those notes.

## Product Contract

### Summary

Add a compound pack of twelve review rules for CI-facing changes. Each rule file carries a stable id, a one-sentence rule, a harm taken from a real incident in this org, a WRONG/RIGHT pair cited as `<repo> <sha>:<path>:<line>`, and a closing `Gate:` line whose check question a reviewer answers from the diff alone. Numbers the diff cannot show (job wall time, setup seconds, PR gate total, daily runner-minutes) live in each run's step summary or in a header comment on the lane, and the rule checks the diff-visible shape that produces them.

### Problem Frame

CI in this org is slow and its main verdicts are unreliable. Measured in this repo and the public org repos:

- A kill cap hid a cause. Five Mutation runs on main in this repo were killed at 30 minutes, for example `systemfsoftware/systemfsoftware` run `35938446772`: "The job has exceeded the maximum execution time of 30m0s" (`systemfsoftware/systemfsoftware e08764fb8f:.github/workflows/mutation.yml:91`, `timeout-minutes: 30`).
- Main went red and stayed red. The Mutation lane on main failed from 2026-09-25 to 2026-10-09: 95 runs, 60 failed, 34 cancelled, 1 passed, 372 runner-hours spent. It ended when #700 switched the push trigger off rather than fixing the cause.
- Main cancels its own verdicts. `ci.yml:10-12` groups by ref with `cancel-in-progress: true`, so `systemfsoftware/systemfsoftware` run `36047298397` was cancelled after 40 minutes, the next run was cancelled too, and the third failed. Main stayed red 3.7 h with no verdict on the first two commits. In `systemfsoftware/stryker-js-effect`, a main-side `cancel-in-progress: false` with no `queue` still replaced pending runs with zero jobs started (runs `38072120191`, `38073244833`, `38073356143`).
- Setup dominates. A public repo's PR lanes spend 559-714 s entering a Nix dev shell before gates that take 9-262 s (`systemfsoftware/effect-endgame-starter-kit` run `37919809442`). A commitlint job here needs a producer job plus a workspace install to lint one commit message.

No existing law owns these rules (the brainstorm's ownership notes), and existing doctrine contradicts some of them (Appendix B).

### Key Decisions

- KD1. **Eleven rule files grouped by outcome, not one file per brief item; a twelfth added by the 2026-10-12 amendment.** R6 and R7 of the brief overlap, so they regroup into a PR-gate rule, a postsubmit rule, a red-main rule and a release rule. Governs R8-R18 and R22. (session-settled: user-approved - chosen over a 1:1 split of twelve or more files: less overlap between files)
- KD2. **Rule id = `ci-wall-clock/<file slug>`.** A slug is never renamed, and a retired rule is deleted outright, with its id never reused. Governs R2.
- KD3. **The workflow decides and the patrol opens the revert PR.** The postsubmit workflow attributes the culprit, judges confidence and files the P0 with `GITHUB_TOKEN`; a user credential opens the revert PR. Governs R15. (session-settled: user-directed - chosen over a workflow-opened revert PR: it depends on an unverified per-repo setting and turning it on is a forbidden settings change)
- KD4. **Every push to main gets its own completed heavy verdict.** Batching and bisection are out of this pack. Governs R14, R15. (session-settled: user-directed - chosen over TAP-style batching: per-commit verdicts make culprit attribution and the automatic revert sound)
- KD5. **Measured rules check the diff's shape; the number lives in the run.** Governs R9, R13, R17.
- KD6. **No separate accessibility lane stays in this pack, inside the PR-gate rule.** Governs R13. (session-settled: user-directed - chosen over citing storybook-testing alone: that loses half of the brief's R9)
- KD7. **Push runs are scoped from the lane's last green main commit, not the full corpus.** Governs R14. (session-settled: user-directed - root ruling 2026-10-11, chosen over a full corpus on every push, about 3,500-4,500 runner-min/day with 31-min jobs, and over a scheduled daily full corpus)
- KD8. **Flake artifacts are built once on main, keyed on their inputs, and restored read-only everywhere else; how they are stored depends on repo visibility.** A public repo carries no credentials and no cloud wiring in CI and stores them in the host CI's own cache or artifacts. A private repo on the fleet's runners stores them in an in-region S3 substituter with signed push from main. Governs R12. (session-settled: user-directed - root ruling 2026-10-11, chosen over the brief's single fleet-cache rule: a public repo carries no credentials and no cloud accounts in CI)
- KD9. **The coding agent's pre-PR UI evidence is not a rule in this pack.** Compound Engineering's ce-test-browser stage owns it, and the README names that stage beside the other owners (R4). Governs R4, R21. (session-settled: user-directed - root ruling at the plan gate 2026-10-11, chosen over a rule file of its own: sandbox UI evidence is not a CI wall-clock rule, and no org incident was found for it, so it would not count under the contract)
- KD10. **The merge freeze is held at the merge decision.** Governs R15. (session-settled: user-directed - chosen over a ruleset or merge-blocking check: both are settings changes)

### Requirements

**Pack shape**

- R1. `compound-packs/ci-wall-clock/` sits beside the six existing packs, with one rule per file, in their exact format: the README shape, the frontmatter keys (`title`, `applies_when`, `tags`, nothing added), the prose `applies_when` style, the `## Rule` section, the WRONG/RIGHT code block with `<repo> <sha>:<path>:<line>` citations, and the closing line ``Gate: `review`.`` followed by the rule's check question. The shape is the one the Compound Engineering Packs guide defines (https://every.to/compound-engineering/guides/packs): `title` and `applies_when` are required, `tags` help matching, each top-level `.md` other than the README is one rule, and the README is the pack's description.
- R2. Each rule's id is `ci-wall-clock/<slug>`. The slugs are exactly those of R8-R18 and R22, and the README lists them in the order R8, R9, R10, R22, R11-R18. The root approved the first eleven ids at the plan gate and the twelfth, `gates-share-one-job`, in the 2026-10-12 amendment; all are frozen under KD2.
- R3. Each rule's `applies_when` names, as concrete situations matched by meaning (never topic labels, and never a path list as the only test), the changes it governs, and its `tags` let resolution by tag find it. Together the rules cover: adding or changing a job, trigger, `matrix`, `concurrency` group, `timeout-minutes` or `paths` filter in `.github/workflows/**`; adding or changing a composite action under `.github/actions/**`; changing a CI-facing flake output, check or package; changing self-hosted runner configuration; changing a machine-image build, AMI or launch template, or the fleet promotion or rollout pipeline; and changing a release or deploy job. Tags include `ci` and `workflows` on every rule, `actions` where a rule governs composite actions, and `machine-image`, `deploy` and `runners` where it governs images, deploys or runners. The README states the same scope.
- R4. The README cites rules owned elsewhere and does not restate them, so each law keeps one owner (CONST-S4). Owners: fix at the cause (`CONSTITUTION.md` CONST-S1); tests of a shipped tool test the published surface (CONST-T8); what is affected is decided by what code is, never by its path (CONST-T12; `.github/AGENTS.md:20`); mutation never on a pull request and never local (`.github/AGENTS.md:21`, `AGENTS.md` REPO-D3); how axe runs inside a story (`compound-packs/storybook-testing/real-browser-axe-as-error.md`); release runs never cancel each other (`docs/solutions/tooling-decisions/pnpm-owns-the-changeset-ledger.md:109`); the coding agent's pre-PR UI evidence, gathered by using the built product the way its user does (Compound Engineering's ce-test-browser stage; KD9).
- R5. `.compound-engineering/config.yaml` enrols `compound-packs/ci-wall-clock`. No other repo is touched.
- R6. Each rule file states one rule sentence, a why from an incident in this org, one WRONG/RIGHT pair and a check question answerable from the diff alone. Every run id names the repo whose run it is. A rule with no public RIGHT exemplar shows the right shape as neutral code with no citation.
- R7. Only repos that the org's repository visibility list lists as PUBLIC are named. A private repo's incident appears only as an unnamed pattern with a date, or is replaced by a public one. Nothing marked UNVERIFIED in the evidence is cited.

**The rules** (the rule sentence and check question are the normative text; the incidents are the required evidence)

- R8. `one-stuck-job-backstop`. Every job that runs steps sets `timeout-minutes: 60`, never another value, above 60 included; no job, step or tool invocation gets a shorter wall-clock kill, each such job writes its wall time to the step summary, and an overrun is fixed at its cause. A job that calls a reusable workflow carries no `timeout-minutes` and passes no other job timeout and no shorter cap through `with:`; the callee's jobs carry the backstop and the summary. A cap that bounds one unit of work inside a job (a mutation runner's per-package `--cap-seconds`) is a kill below the backstop too; there is no per-unit exemption. Its gate is review.
  - **Check:** Does any non-caller job in the diff (a job with `runs-on`) set `timeout-minutes` to anything other than exactly 60 (67, 75 and 120 fail as 5 and 30 do), omit it, or take it from an input whose default is not 60? Does any step set one below 60, any command run under a wall-clock kill below 60 minutes (a `timeout N` wrapper, a runner's whole-run timeout flag, a lane-level cap handed to a tool such as a planner's `max-seconds` or a per-package `--cap-seconds`), or any such job leave its wall time out of the step summary? For a `uses:` caller job, does its `with:` block pass a value other than 60 into an input the callee turns into a job's `timeout-minutes`, or a value below 60 into one the callee turns into a step or tool cap (`plan-timeout-minutes`, `gate-timeout-minutes`, `max-seconds` or an equivalent, including a field inside a structured input such as a lane list's `"timeout-minutes"`)? Each such input is resolved to the callee's cap that consumes it, read at the ref the caller pins. A caller job that only omits its own `timeout-minutes` passes. A per-test timeout inside a test framework is out of scope.
  - **WRONG:** `systemfsoftware/systemfsoftware e08764fb8f:.github/workflows/mutation.yml:91` (`timeout-minutes: 30`). `systemfsoftware/systemfsoftware` run `35938446772`, job `Mutation (packages/effect-readiness)`, was killed at 30m0s, and four more runs died the same way (`35887715884`, `35991344744`, `36010116451`, `36070566247`). The cause was one package concentrating too many mutants, later fixed by splitting it (`docs/solutions/architecture-patterns/mutation-budgets-split-rule-packages-into-private-cells.md`). Caller form: `systemfsoftware/systemfsoftware 02bf9653b1:.github/workflows/ci.yml:70-73` hands the callee's lane jobs `"timeout-minutes": 45` and `30` through `with:`, applied at `reusable-checks.yml:408`.
  - **RIGHT:** `systemfsoftware/systemfsoftware 02bf9653b1:.github/workflows/reusable-checks.yml:381` (`timeout-minutes: 60`), the job #735 added at the backstop; on its branch the job first carried 10, raised by `e9543bae65`, whose message is "give every job this branch adds the 60-minute stuck-job backstop". Also `systemfsoftware/gritlint 5c9c2ab:.github/workflows/mutants.yml:33`.
  - **Grounds:** GitHub, "Reusing workflow configurations", section "Supported keywords for jobs that call a reusable workflow" (https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations): "When you call a reusable workflow, you can only use the following keywords in the job containing the call", a list of `name`, `uses`, `with`, `secrets`, `strategy`, `needs`, `if`, `concurrency`, `permissions` and `cache-mode`.
- R9. `setup-under-a-minute`. A PR job reaches its first verdict step within 60 s: only checkout, one pinned tool fetch, a cache or substituter restore, a frozen install and R13's affected-set base lookup come before it, never a source build; a task runner's `build` inside the verdict invocation is part of the verdict step. A PR job may build an artifact without saving it in two cases only: its diff changes that artifact's inputs, or the restore of main's key misses (for example, after eviction). R12 cites these two cases.
  - **Check:** Does any pull-request job in the diff run a source build, a workspace bootstrap, or anything else beyond checkout, one pinned tool fetch, a restore, a frozen install and the affected-set base lookup, before its first verdict step? Building an artifact without saving it passes only when the diff changes that artifact's inputs, or when the build step sits behind a restore keyed on the artifact's input hash so that a hit skips it.
  - **WRONG:** `systemfsoftware/pnpm-release-management 8cd6e83009:.github/workflows/changeset-check.yml:66-71` builds the release tools with `nix build` on every PR. In `systemfsoftware/systemfsoftware` run `38105407053`, this repo's caller run of that reusable, the step took 119 s of a 160 s job.
  - **RIGHT:** `systemfsoftware/systemfsoftware 02bf9653b1:.github/actions/install-deps/action.yml:17,27`: a Node runtime and `pnpm install --frozen-lockfile`, 17 s in `systemfsoftware/systemfsoftware` run `38113391870`. The citation shows only the setup shape; the job that ran it is condemned by R13.
- R10. `light-checks-run-the-pinned-tool`. A commit-message, changeset or PR-title check runs its pinned tool directly, with no workspace install, dev shell or producer job before it.
  - **Check:** Does a commit-message, changeset or PR-title job in the diff install the workspace, enter a dev shell, or `needs:` another job before running its tool, or take its tool from anything but one pinned fetch (a floating `dlx` or `npx`, or a tool version left as a range: `@latest`, a bare major such as `@2`, or a setup action's version input left unset)? - R11. `no-dev-shell-on-verdict-lanes`. No lint, typecheck or test job enters a Nix dev shell.
  - **Check:** Does any lint, typecheck or test job in the diff run `nix develop`, a dev-shell action, or a command wrapped in one?
  - **WRONG:** `systemfsoftware/effect-endgame-starter-kit 375e468:.github/workflows/ci.yml:49,59`. - R12. `flake-outputs-build-once-on-main` (renamed from the draft slug `flake-outputs-substitute-from-the-binary-cache`, which named only the private case; the root approves ids at the plan gate). A flake artifact CI uses is built on main only when its inputs change or the restore of its key misses (for example after eviction), keyed on its input hash (for example the `flake.lock` narHash or the drvPath), written from main only, and restored read-only by every PR job and every agent sandbox that can reach the cache, neither of which rebuilds an artifact main already built for the same inputs. A PR job builds it without saving only in R9's two cases: its diff changes the artifact's inputs, or the restore of main's key misses. A PR's flake check restores what main cached and builds only the uncached derivations its input changes produce, and the flake keeps full VM tests and machine images out of `checks` (for example under `packages`, evaluated but not built) so main builds them by name; plain `nix flake check` evaluates and builds the checks, and `--no-build` is used only when evaluation is the check intended.
  - **Public repos:** CI carries no credentials and no cloud wiring: no OIDC role, no S3, no fleet substituter. The artifact lives in the host CI's own cache or artifacts. Main writes it; a PR job restores it through a restore-only form (`actions/cache/restore`, or `cache-mode: read` on the job).
  - **Private repos on the fleet's runners:** an in-region S3 substituter, signed push from main only, PR jobs read-only. Here an artifact never travels through `actions/cache` alone. The runners trust only the substituter's signing key, and only main pushes.
  - **Agent sandboxes and CI:** a result computed once on main is reused read-only by PR jobs and coding-agent sandboxes through the cache the repo already has. A sandbox never writes it and is given no credential; where it cannot reach the cache (a public repo's host-CI cache), it builds locally and writes nothing back.
  - Neither case depends on any unmerged runner change.
  - **Check:** (1) Does a pull-request job build an artifact in a step that no restore keyed on the artifact's input hash comes before, so a hit cannot skip the build (a `nix build` on a runner with no substituter main pushes to, a build whose `if:` does not read the restore's hit), when the diff does not change that artifact's inputs? A substituter the runner reads is that restore, keyed on the drvPath. Whether main's key actually missed is runtime state; review checks the guard, not the hit. (2) Does a public repo's workflow name a credential or a cloud role (`id-token: write`, a cloud login action, an S3 or substituter secret)? (3) Does a pull-request job write the artifact through an `actions/cache/save` step, a substituter push, or a job without `cache-mode: read` (set at job or workflow level) whose steps save? (4) In a private fleet repo, does the artifact travel through `actions/cache` alone, or does the workflow carry a signing key? (5) Does a pull-request job run plain `nix flake check` where it means to evaluate only, or `--no-build` where it claims the checks build? (6) Does the diff give an agent sandbox a way to write the cache (a save or push step, a cache or substituter credential), or add a credential so a sandbox can reach a cache it could not reach before?
  - **WRONG:** `systemfsoftware/systemfsoftware 02bf9653b1:.github/actions/sfs-deps/action.yml:94-95` saves the tarball cache on a miss from any event, pull requests included, and `.github/workflows/reusable-checks.yml:379-390` and `reusable-commitlint.yml:27-31` each run their own producer of the same key. #735's body: "A caller that runs several of these reusables in one run can build once per call on a cold cache."   - **RIGHT:** neutral shapes, no citation. Private fleet: the runner trusts the substituter's signing key, a main-only job pushes signed paths after building, and PR jobs only substitute.
  - **Grounds:** GitHub, "Dependency caching reference", section "Restrictions for accessing a cache" (https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching): "Workflow runs can restore caches created in either the current branch or the default branch (usually `main`). If a workflow run is triggered for a pull request, it can also restore caches created in the base branch", and "When a cache is created by a workflow run triggered on a pull request, the cache is created for the merge ref (`refs/pull/.../merge`). [...] It cannot be restored by the base branch or other pull requests targeting that base branch." The same page, section "Controlling cache access with `cache-mode`", gives `read` as "Restore caches: Yes, Save caches: No", and recommends "a restore-only cache operation such as `actions/cache/restore`". A PR write is therefore wasted for every other run, which is why only main writes.
- R13. `pr-gate-runs-only-what-the-diff-affects`. The PR gate runs only what the diff affects, decided from the dependency graph, never from a package or path list the workflow maintains by hand: lint and typecheck, property tests, public-API feature tests with IO emulated, and the changed Storybook stories with their interaction, a11y and visual checks. A pull request compares against its base commit; a push to main compares against the last main commit whose run of the same workflow succeeded, checked as an ancestor, never `HEAD~1`, and runs everything when none is found. Every file CI runs or tests that no package owns is declared in the graph (as a package, or in the task runner's repo-wide inputs such as turbo's `globalDependencies`), because an affected run that selects nothing runs nothing and passes: turbo 2.11.5 exits 0 on an empty selection. The job checks out full history (`fetch-depth: 0`; `filter: tree:0` acceptable). It fits in 10 minutes. Heavy suites, full VM tests and machine-image builds never run in any job a pull request reaches (a flake whose PR job runs `nix flake check` keeps them out of `checks`, so the check still builds every ordinary check), and no CI job has accessibility as its only subject outside the story run. Where a repo's plan adopts GitHub's native merge queue, it may be used; the rule does not require one. The review of a diff that changes a workflow, an action, a CI-facing flake output, runner configuration, a machine-image build or a deploy pipeline runs on ce-code-review's full path, and the PR body carries its receipt listing every declared pack as loaded; a receipt saying no pack loaded fails.
  - **Check:** Does a pull-request job in the diff run something the diff does not affect, decide what is affected from a path instead of the build graph, run a heavy suite (full-stack e2e, full corpus, mutation), or have accessibility as its only subject outside the story run? In a repo with a dependency graph (a workspace task runner, or flake derivations), does a job in the diff choose what to run from a package or path list it maintains by hand (`paths:` filters, a hard-coded package list, a `--filter` naming packages) instead of the graph's affected output? Does the diff add, move or change a file a CI job runs or tests that sits outside every package and outside the task runner's repo-wide inputs, so the affected set can never select it? Does a main-push job compare against `HEAD~1`, `github.event.before` or anything but the last main commit whose run of the same workflow succeeded, checked as an ancestor? Does its base lookup name a workflow file other than the one it runs in, or fail the job when the lookup fails instead of running everything? Does an affected computation run on a checkout or fetch without full history (`fetch-depth` other than 0, or `git fetch --depth`)? Can a `pull_request` trigger in the diff reach, directly, through `needs:` or through a called reusable workflow, a job that runs a main-only suite, a full VM test or a machine-image build, including a flake that puts a full VM test or an image under `checks` where a pull request runs `nix flake check`? For a diff that changes a workflow, an action, a CI-facing flake output, runner configuration, a machine-image build or a deploy pipeline: does the PR body carry a full-path ce-code-review receipt listing every declared pack as loaded, ci-wall-clock among them? A missing receipt, or one that says no pack loaded or names the lite or focused path, fails.

Neutral WRONG (image matrix on `pull_request` with a Nix path filter) and RIGHT (plain `nix flake check`, with the VM test and images outside `checks`) in the rule file.
  - **WRONG:** `systemfsoftware/systemfsoftware 02bf9653b1:.github/workflows/ci.yml:86-103`.
