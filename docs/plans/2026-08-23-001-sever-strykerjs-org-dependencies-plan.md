## Product Contract

### Summary

Six of the eight upstream packages the workspace's mutation tooling was built on are already `@systemfsoftware` forks (`plugin-api` ← api, `mutation-run` ← core, plus `typescript-checker`, `vitest-runner`, `mutation-report`, and `cli`). Two remain un-forked npm dependencies — `@stryker-mutator/util` (18 modules, 480 lines, zero runtime deps) and `@stryker-mutator/instrumenter` (~60 modules, 3,644 lines, Babel-based) — and `@stryker-mutator/api` survives only as vestigial manifest entries (zero source imports remain; `plugin-api` is its Effect fork). This change forks the two, re-points every consumer import, deletes the vestigial entries, swaps the published default plugin glob from `@stryker-mutator/*` to `@systemfsoftware/stryker-js-*`, and removes the org from the catalog and dependabot. Line counts are point-in-time measurements of the 9.6.1 tarballs read this session.

### Problem Frame

The workspace self-hosts its mutation tooling (REPO-O1: ported packages are owned outright), yet every mutation run still resolves the instrumenter and util from the strykerjs org at install time. Upstream is pinned at 9.6.1 and already diverged from this tree's TypeScript 7 reality — the core fork exists precisely because upstream calls removed TS6 APIs. The remaining two packages are the last external resolution edges into an org whose release cadence, breaking changes, and API assumptions this tree does not control.

### Key Decisions

- No dependency on the strykerjs org survives anywhere the workspace resolves code. (session-settled: user-directed — chosen over pinning upstream: the goal is independence, and a pin keeps the external edge.) Governs R1–R4, R7.
- Code authored fresh in this change follows the repo's Effect sandwich doctrine (impure read → pure decide in `Workflow.make` → impure write); verbatim-forked upstream source keeps upstream idioms, the same accommodation every sibling fork's leaf `AGENTS.md` records (CONSTITUTION §V.6). (session-settled: user-directed — chosen over rewriting the forks in Effect: the instruction names forking under `@systemfsoftware` as a sanctioned path, and this change authors no new decisions inside the forked code.) Governs R5, R6.

## Planning Contract

### Key Technical Decisions

- KTD1. Verbatim source fork, not an Effect rewrite, for both packages. The instrumenter is 3,644 lines of Babel AST transforms (mutators, placers, parsers, printers) feeding the mutation gate of every package in the tree; a house-style rewrite risks semantic drift in exactly the machinery this repo's CI depends on, and the user's instruction sanctions forking under `@systemfsoftware` as a path. Sibling precedent: all six existing forks kept upstream idioms with a leaf `AGENTS.md` accommodation. Rejected alternative: strict Effect-TS rewrite — right end-state, wrong PR; it needs its own plan and budget. This decision is unlabeled (the fork-vs-rewrite choice was not examined with the user); the adversarial challenge it received is recorded in Appendix.
- KTD2. `@stryker-mutator/api` is deleted, not forked. Zero source imports remain anywhere (verified by session grep over all `packages/` sources); `@systemfsoftware/stryker-js-plugin-api` is its published replacement. The entries in `mutation-run`/`mutation-report` dependencies and `stryker-plugins` dev/peer dependencies are dead weight.
- KTD3. Import re-pointing map, applied mechanically: `@stryker-mutator/util` → `@systemfsoftware/stryker-js-util`; `@stryker-mutator/instrumenter` → `@systemfsoftware/stryker-js-instrumenter`; inside the instrumenter fork, `@stryker-mutator/api/{core,plugin,logging,ignore}` → `@systemfsoftware/stryker-js-plugin-api/{core,plugin,logging,ignore}` (all four subpaths exist in `plugin-api`'s exports map, verified this session). The `declare module '@stryker-mutator/api/ignore'` augmentation in `transformers/ignorer-bookkeeper.ts` re-points to `@systemfsoftware/stryker-js-plugin-api/ignore`.
- KTD4. Plugin discovery self-hosts, best-effort exactly as upstream's is. Default `plugins` becomes `['@systemfsoftware/stryker-js-*']` in `plugin-api`'s `StrykerOptions.schema.ts`. The loader's org-directory resolution (`plugin-loader.ts` `globPluginModules`) currently walks five URL levels up from the module — correct only for upstream's `dist/src/plugins/` nesting. The fork emits a flat `dist/plugins.mjs`, and source-condition runs nest differently again, so the fix resolves the org directory from a sibling package's resolved URL (`import.meta.resolve('@systemfsoftware/stryker-js-plugin-api/package.json')` → dirname of its dirname) and `readdir` failure on a missing directory returns an empty list instead of throwing. Honest reach, matching upstream: glob discovery finds org siblings under hoisted layouts (npm installs, this workspace); under pnpm-isolated adopter installs it finds only the resolved sibling's own store neighborhood, exactly as upstream's glob does — such installs list `plugins` explicitly, and the no-throw guarantee plus the warning for non-default globs is the contract. `IGNORED_PACKAGES` gains the fork's non-plugin names (`util`, `instrumenter`, `plugin-api`, `mutation-run`, `mutation-report`, `cli`; upstream's `core`/`api` stay harmlessly). The change stays in upstream idiom inside the forked file (minimal diff).
- KTD5. New-package scaffold copies the siblings exactly: manifest fields mirroring `typescript-checker`/`vitest-runner` (repo URL, `files`, tsdown-managed exports — never hand-edited, REPO-S4), tsconfig reproducing upstream strictness with a comment naming the fork, `tsdown.config.ts` with `exports: { devExports: '@systemfsoftware/source' }`, externalized `dependencies` carrying upstream's exact ranges (babel stack, `angular-html-parser`, `semver` via `catalog:stryker`, `tslib` via `catalog:stryker`, `weapon-regex` for instrumenter; none for util), version `0.1.0`, `attw --pack .`, provenance-publishing `publishConfig`. The published surface is the verified artifact (tsdown-generated exports + attw on the packed tarball), matching the repo's settled publish-surface verdict.
- KTD6. `frameworkPluginsFileUrl` needs no rewiring at the source level: it is `import.meta.url` in `frameworks/index.ts` and self-references whatever build emits it. The build-level proof is U2 scenario 3 — the dynamic `import(frameworkPluginsFileUrl)` test is the gate, not decoration: if tsdown chunk hashing ever splits the URL-bearing module from the framework exports, the sandbox loads a module without the ignorer plugin, and only that test fails. If it fires, the remedy is keeping both in one chunk (`tsdown` `advancedChunks`/entry pinning), never re-pointing the URL by hand.
- KTD7. Changesets follow the turbo-hash gate, not file-touch reasoning: new packages demand their first intents; manifest edits re-hash the touched consumers; catalog-only edits demand nothing (the gate's known owned gap, reviewed in the release pass).
- KTD8. Verification relies on existing surfaces, not authored ceremony: upstream ships no tests in the tarball (same as every sibling), so behavioral proof comes from (a) the consumers' existing suites, (b) `cli`'s integration contract test running real mutation runs over five fixture projects through the shipped bin, (c) one authored characterization spec for the instrumenter fork (warrant: characterization before restructuring — it pins instrumented output bytes so wiring mistakes that typecheck can't see — wrong entry, dropped module, broken globals — fail a test), and (d) the CI Mutation workflow on the PR (advisory by construction; REPO-D3 forbids local runs).

### Assumptions

- The fork base is the lockfile-pinned `@stryker-mutator/{util,instrumenter}@9.6.1` tarball sources under `node_modules/.pnpm/…/src/` — complete TS sources (verified: 18 files/480 lines for util; ~60 files/3,644 lines for instrumenter) with `LICENSE` in each tarball. Before copying, the implementer re-verifies the pin (`pnpm ls @stryker-mutator/instrumenter @stryker-mutator/util` shows `9.6.1`) and re-checks the file counts against this line, so a floating catalog resolution cannot silently become the fork base.
- Every in-tree `stryker.config.json` either sets `plugins` explicitly or extends `@systemfsoftware/stryker-js-mutation-run/config/base`, whose preset sets them to the fork plugin names (verified this session by enumerating all 18 configs and reading `src/config/base-preset.ts:24-29`; the six that omit `plugins` all extend the base) — so the default-glob path is inert in-tree today; U3 re-asserts by enumeration before the default flip, because a config relying on the default glob would change behavior silently and no other gate sees config semantics.
- Re-pointing scope: the instrumenter fork carries 29 `@stryker-mutator` import sites across 21 files (plus the `declare module` augmentation); `mutation-run` carries ~37 sites across 34 files; `cli`, `vitest-runner`, and `typescript-checker` one or two each. Non-import occurrences in consumer sources (doc-comment examples in `plugin-loader.ts` `:57-58`, `:117`, `:216-217`; the comment in `cli/src/cli-request.schema.ts:10`) are in scope too — the zero-sweep gate is unachievable with import-only re-pointing.
- The forks publish (R8), so their script sets follow whichever published sibling (`typescript-checker` or `vitest-runner`) matches their test surface — `effect-cell-gen`'s reduced-script case is not precedent because it is unpublished. No `--passWithNoTests` ceremony.

### Sequencing

U1 (util fork) → U2 (instrumenter fork) → U3 (consumer rewire + discovery fix) → U4 (root cleanup + sweep) → U5 (verify + intents). U1 and U2 can be prepared in either order, but U2's manifest depends on U1 existing (its `workspace:^` to `@systemfsoftware/stryker-js-util` must resolve at install), so U1 lands first; U3 requires both.
