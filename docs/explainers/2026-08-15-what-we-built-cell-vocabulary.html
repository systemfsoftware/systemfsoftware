Subject

Strip away every abstraction and this change is about a list of five words: read, decode, decide, encode, write. Before, that list — plus which of those are allowed to touch the outside world — was typed out by hand in five different packages. Now it is typed once, and the other four read it off a value at runtime.

That's the whole idea. Everything below is why it mattered, what it cost, and how to watch it work.

1. The thing being described

A Cell description is a recipe for one operation, written as a chain. You read something, decode it, make a decision, encode the result, write it back. Five steps, always that order.

Two of those steps are allowed to touch the world — read and write do I/O. The three in the middle are pure: they take a value and return a value, no database, no clock, no filesystem. That split is the point of the whole shape, because it means all the messy parts are at the two ends and the decision logic in the middle is testable in isolation.

You build one by calling constructors that only fit together in one order: 

// each call's return type is the next call's required argument type,
// so a wrong order does not compile — the order is a type fact
Cell.write(
  Cell.encode(
    Cell.decide(
      Cell.decode(
        Cell.read(fetchTheRow),
        parseIt),
      decideWhatToDo),
    formatTheAnswer),
  saveIt)

2. What was actually wrong

The chain worked. The problem was everything else that needed to know those five words.

A lint rule enforces "no database calls inside a pure step". To do that it must know which steps are pure. On main, it knew by having the answer typed into it:

Before — a lint rule's own file

export const DESCRIPTION_SOURCE =
  '@systemfsoftware/effect-cell-types'

export const PURE_PHASES =
  ['decode', 'decide', 'encode']

export const IO_CELLS =
  ['store', 'adapter']

export const IO_SOURCES =
  ['effect/Clock', 'effect/System']

After — the same file

export const DESCRIPTION_SOURCE =
  Cell.vocabulary.module

export const PURE_PHASES =
  Cell.vocabulary.byKind.pure

export const IO_CELLS =
  Cell.vocabulary.ioCells.cells

export const IO_SOURCES =
  Cell.vocabulary.ioCells.sources

Four facts, hand-copied on the left, read from the source on the right. Same values today — that's exactly why the left version was dangerous. Nothing was broken, nothing failed, and no test could tell you the copy existed.

Here is the failure mode, concretely. Suppose you add a sixth step called validate, and it's pure. The description now has four pure steps. The lint rule still has three in its list. So a developer writes a database call inside a validate body and the rule says nothing — it isn't watching that step, because nobody told it the step exists. The build is green. The guarantee is gone. You find out when something breaks in production, and the reason is a list in a file nobody thought to update.

That copy existed in five places: the description itself, two lint rules, and two more consumers added along the way. Five places to update, no alarm if you miss one.

3. What replaced it

The description now carries its own vocabulary as data. You can print it: 

$ node -e "import {Cell} from '@systemfsoftware/effect-cell-types';
           console.log(Cell.vocabulary)"

{
  module: '@systemfsoftware/effect-cell-types',
  ioCells: { cells: ['store', 'adapter'],
             sources: ['effect/Clock', 'effect/System'] },
  byKind:  { pure:   ['decode', 'decide', 'encode'],
             impure: ['read', 'write'] },
  applier: 'apply',
  phases:  [ ['read',   'impure', 'effect'],
             ['decode', 'pure',   'either-fail'],
             ['decide', 'pure',   'either-pass'],
             ['encode', 'pure',   'total'],
             ['write',  'impure', 'effect'] ]
}

That output is not a table someone typed. It is computed by walking a real description built with the public constructors — the same constructors any caller uses. The walk reads the phase records out of the built value and groups them.

This is the part worth slowing down on, because it's the difference between this change and a cosmetic one. If the vocabulary were a hand-written table sitting next to the constructors, it would be a sixth copy — better organised, still a copy, still able to disagree with the constructors. Because it is a fold of a value the constructors produced, it cannot disagree with them. There is nothing to keep in sync.

The five things it carries

AxisWhat it answersWho needs it
phases[].nameWhat are the steps called?every consumer
byKindWhich steps are pure vs do I/O?the lint rules
phases[] orderWhat order do they run in?the type-test generator

ioCellsWhich calls count as touching the world?the lint rules

4. Who reads it

Four consumers, four packages, four different jobs, none of which types out a phase name. The generator draws random-but-valid descriptions by substituting random functions into the walked shape. The type-test package emits compiler assertions from the walked order. The two lint plugins decide what they forbid from the walked purity and I/O sets.

5. The test that this is real

Claiming "it's all derived now" is cheap. The experiment that makes it falsifiable: add a sixth step and change nothing else. If a consumer is genuinely derived, it stays green and its output changes. If it stays green with unchanged output, it never saw the new step. If it breaks, it was holding a copy.

That was run. A sixth pure step named validate was added inside the description file only. Result:

  • Every consumer package stayed green with a step it had never heard of.
  • Their output changed: the generated type-test suite grew assertions for validate, and the lint rules' pure set gained it.
  • The only failures were inside the description package itself — its own hand-written check, its API snapshot, and its type spec. Those are supposed to fail: they are the things that exist to disagree.

Reclassifying an I/O cell was tested the same way: one file changed, the rules' forbidden-call set changed, whole build green.

Honest limit. That experiment was performed and recorded; the script that automated it was deleted along with a mechanism it was built beside, so repeating it means making the edit by hand. The measurement is dated, not re-runnable on demand.

6. The one hard problem, and what it cost

A lint rule reading the description means the lint package must import the description package. That created a dependency loop: 

effect-executor  →  effect-cell-types  →  effect-gherkin-spec
       ↑                                          ↓
   effect-dmmf   ←──────────  oxlint-config  ←────┘

Read it as: the lint plugin wants the description; the description package lints itself using the shared lint config; the shared lint config bundles the lint plugin. Circular. The build tool refuses.

The fix was to stop bundling that plugin in the shared config, and have each package that needs it load the plugin itself. The loop opens, the direct import becomes legal, and no generated intermediate file is needed.

That trade has a hidden cost, and it's the most useful thing in this whole change to understand. When the shared config bundled the plugin, every package that used the shared config got those rules automatically — forgetting was impossible. Now each package opts in by hand. So a package created next month with one of these files in it simply does not get the rules, and nothing complains. The guarantee didn't move; it evaporated.

So a check was added: the lint-coverage guard now fails when a package owns one of those files and its own config doesn't load the matching plugin. It was watched failing with one package's entry deleted, and passing with it restored.

The general lesson, worth more than the specific fix: trading an automatic guarantee for a convention is not a simplification. It only becomes one once something fails when the convention is broken.

7. What also changed that you'd notice

The description's internal shape changed, and this part is a real breaking change:

Before — five optional slots

interface Layer<P> {
  readonly read?:   ReadPhase<P>
  readonly decode?: DecodePhase<P>
  readonly decide?: DecidePhase<P>
  readonly encode?: EncodePhase<P>
  readonly write?:  WritePhase<P>
}

After — an ordered list

interface Layer<P> {
  readonly phases:
    readonly Phase<P>[]
}

// each Phase carries its own
// name, kind, convention, run

The left shape cannot be walked usefully: to find out what's in it you must already know the five field names, which is the same as having the list written down. The right shape can be walked by anything — that single change is what made every consumer possible.

If you built descriptions with the constructors, nothing breaks. If any code read layer.decode by name, it now reads the array instead.

8. Does it work — the evidence

  • pnpm check:local — 281 tasks, all pass, run after the last edit.
  • All four CI workflows green on the pushed head, including the 30-job mutation matrix and the full gate.
  • Mutation testing at 100% on both lint plugins: every deliberately-introduced bug in the rules is caught by a test. Zero survivors, zero uncovered, zero ignored.
  • No dependency cycle: the build tool reports a clean graph.
  • A nine-lens review ran over the diff. Seven reviewers independently found the same gap — the missing delivery check from section 6 — which is now closed.

9. What is still open

  • known The generated type suite has one blind spot: a step added to the types but never registered in the real chain produces no assertion. It is written down in that package's own notes.
  • known In packages that load both lint plugins, one violation is reported twice, because the newer rule's reach is a superset of the older one's. Retiring the older one would lose coverage in the single package that loads only it — so this needs a decision, not a quick edit.
  • known The lint rules read the vocabulary from the description's built output. Editing the description and linting a single package without rebuilding judges against the previous build.

The one-sentence version

A list of step names and which of them may touch the world used to be typed into five packages; now the description computes it from the value its own constructors build, four packages read it from there, and a new check makes sure those packages actually receive the rules that depend on it.
