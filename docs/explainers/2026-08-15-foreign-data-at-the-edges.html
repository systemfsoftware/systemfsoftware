Foreign data at the edges — what today's argument was actually about

Date
2026-08-15
Input shape
concept
Subject
Why data from outside your program needs a border, and the three rules that guard it

Everything today circled one sentence: a type is a promise you made, not a fact you checked. The rest — cells, laws, brands, provenance, ownership — is machinery for deciding where that promise has to be paid for with an actual check.

The confusion is fair, and some of it is mine: the position moved twice today. It started as "two laws," survived two reviewers who broke five of its six rules, then an outside critic dissolved the framing, and it ended as three rules. This walks the whole ladder in order.

1. Start with the bug, because everything else is a response to it

Someone wrote this inside a file that declares domain data. It compiles. Every lint rule in the repo passes it. It is completely broken. 

// TxFinalized comes from a vendor's SDK — someone else's package
type ChainEvents = TxFinalized['events']

const Schema = S.declare(
  (input: unknown): input is ChainEvents => Array.isArray(input),
)

Line 2. Your domain type is now defined as the vendor's type. When they change theirs, yours changes — silently, on a dependency bump.

Line 5. The runtime check says "is it an array?" The type says "it is an array of chain events." Those are not the same claim. Any array passes.

I rebuilt that defect against a Stripe-shaped SDK type and ran it. This is the real output, not a description of one:

A. lying guard accepts junk: ACCEPTED (leak)
B. value produced: {"id":"in_9","amount_due":"not-a-number","currency":42}
C. amount_due is typed number | null, actually holds: string
D. vendor adds a status value → lands in default, silently

The file type-checks clean. That is the whole finding. Not "this is risky" — the compiler is satisfied while a field declared number | null holds the string "not-a-number".

2. Why the compiler can't catch it

TypeScript's types are erased before the code runs. Nothing checks them at runtime unless you write the check yourself. So there are exactly three ways a value gets its type, and only one of them involves reality:

HowWhat actually happensWorth
x as Money You assert it. Nothing is examined. A promise
S.declare(pred) Your predicate runs. It checks whatever you wrote — here, "is it an array". Worth exactly as much as the predicate
decode(schema)(x) Every field is examined against its declared type; failure is a value you must handle. A fact

The bug used the first two. The fix is to make the third one the only door.

3. The border

Picture the program as a country. Outside it: vendors, databases, queues, files — all of them sending you rumors. Inside: your decisions, which must run on facts. There has to be a border, and it has to be one place, or it isn't a border.

Left to right: the vendor's payload arrives; a wire cell states the shape you expect using nothing but primitives; the ACL decodes it, examining every field, and either produces a domain value or fails; the kernel only ever sees what came out the right-hand side.

4. The three rules, and the case each one alone catches

This is the part that changed shape today. It started as two rules. An outside critic argued it should be one. Running the code showed it is three — because for each rule there is a broken program that only that rule rejects.

Rule 1 — Dependency rejection: what may be called

A pure decision function must not read a file, hit a clock, or call the network. Gather first, decide on the gathered values, act on the decision. This is the old rule and nothing today touched it.

Only-it case: readFileSync inside a kernel. The types are all yours, every value was properly constructed — and the code is still in the wrong place.

Rule 2 — Representation ownership: what may be named

A file that declares domain data may only name types your workspace authored. Not the vendor's type, and not a local alias that re-exports the vendor's type — that hop was the hole the critic found in my first version, and it was real: a text-matching rule sees ./vendor-types.js and shrugs.

Only-it case: naming the vendor's type with an honest checker. Every value gets validated, so minting is fine — and you still break when the vendor widens a union next release, which is output D above.

Rule 3 — Minting discipline: how a value comes to exist

A domain value must be produced by something that re-examines it. Decode, or a constructor that parses. Not a cast, not a hand-written guard that checks less than it claims.

Only-it case — and this is the one I ran to settle the argument. Take a type you wrote yourself, from primitives, naming no vendor at all. Ownership: satisfied. Dependencies: satisfied. Then attach a lazy guard: 

type SettledInvoice = { id: string; amount_due: number | null; currency: string }

const Schema = S.declare(
  (input: unknown): input is SettledInvoice =>
    typeof input === 'object' && input !== null && 'id' in input,
)
1. ownership satisfied, lying recognizer accepts junk: ACCEPTED (leak)
2. amount_due declared number|null, actually: string
3. currency declared string, actually: number
4. same junk through a re-parsing constructor: REJECTED

Two of the three rules are fully satisfied and the corruption is total. Line 4 is the rule that stops it. That result is why "ownership plus dependency rejection" isn't the complete set, and it's the strongest thing produced today.

5. What broke when the rules were tested

Two reviewers attacked the first version with runnable probes. Five of six rules failed. Keeping this list honest matters more than the rules looking good — every row was reproduced, not argued.

ClaimResult
"A vendor's change fails loudly at the wire cell." False. 12 of 26 fields were silently dropped — the decoder ignores unknown keys by default.
The production example I cited as the reference. Same hole. It drops vendor fields too. A reference implementation was teaching the bug.
"Only a decoder can mint a branded value." False. One optional argument skips every check. The brand is a name; a name forces nothing.
"Three provenance stamps prove three sources." False. Three stamps from one source passed; stamps 8 hours apart passed.
"A cast poisons the domain." Held — better than claimed. The next real constructor re-checks and rejects it. A cast is a puddle, not a flood.
"Decode-only translation actually holds." Held under both reviewers, including attempts to sneak around it.

The repairs follow directly: tolerate unknown fields when serving traffic but catch them in a test against a recorded payload; give every branded type a constructor with no escape hatch; require provenance to name distinct sources inside a time window.

6. The words, plainly

Cell
One file with one job, its job announced by its filename suffix — .kernel.ts decides, .executor.ts does I/O, .schema.ts declares data, .acl.ts translates.
Wire cell
Your restatement of someone else's payload shape, written in primitives. Their contract, in your words.
ACL (anti-corruption layer)
The translation step. Foreign shape in, domain value out, one direction only — encoding back is refused so the two shapes can't quietly merge.
Decode
Run the data against the schema, field by field, and get back either a value or a failure you must handle.
Brand
A tag in the type that says "this was checked." It exists only at compile time, which is exactly why it needs a constructor guarding it.
Minting
How a value of a domain type first comes into existence. The whole game is making decode the only way.
Provenance
Where a value came from and when it was observed — recorded on aggregates because three sources read at three moments may not describe one consistent world.

7. Still open

  • Rule 2 needs type information to enforce, and the current linter has none. So it ships either as a tsc-backed checker or as a constraint the code generator enforces when it emits cells.
  • A vendor can change what a field means without changing its name or type — dollars becoming cents. Only a recorded payload pinned to its expected decoded value catches that.
  • When three sources disagree because one is stale rather than wrong, is a typed failure right, or should the aggregate be allowed to say "partial"?

If you keep one thing: data from outside is a rumor until something examined it. Types don't examine anything — decoders do. Every rule today is a different answer to "where is the examining supposed to happen, and what stops someone skipping it?"
