Killed-or-Disposed: How a Workflow Reaches 100%

Date
2026-08-16
Input shape

Subject
The mutation gate on workflow files — what a 100% score actually claims, why a literal 100%-killed is impossible, and the four mechanisms in this repo that make the honest score reachable

1. The survivor that cannot die

Mutation testing flips small things in your code — a string literal, a boolean, an arm of a match — and runs the tests after each flip. A test that fails killed the mutant. A mutant every test still passes on is a survivor: either a test gap, or dead weight in your code that nothing observes.

The ceiling problem: some mutants are equivalent — the flipped code is syntactically different but does exactly the same thing. No test can kill one, because there is no behavioral difference to observe. Worse, deciding whether a mutant is equivalent is undecidable — no automated technique can identify them all (Papadakis et al. 2019, canon band in the corpus; the finding traces to DeMillo 1978 and Jia & Harman 2011).

So a literal "100% of mutants killed" is not a number any suite can verifiably reach. That leaves two dishonest exits, and both are banned here:

  • Suppress the survivor — an ignore comment that hides it from the count. The gate goes green while certifying tests that notice nothing.
  • Lower the gate — drop the threshold until the residue stops mattering. The number stops being a claim about anything.
The repo's definition, from the killed-or-disposed-mutation ruling (B5): the gate stays at 100, and 100 means every mutant is killed by a test or disposed — excised with a named, reviewable reason. Disposition is a proof obligation, not an escape hatch. Suppression comments are banned outright; a threshold is never lowered.

2. The one file, both fates

This is a real workflow — packages/effect-daemon-spec/src/internal/restart-decision.workflow.ts, the entire decision a supervision tree makes when a child dies. One file contains both mutant populations:

// disposal zone — declarations and identity, not behavior
const RestartDecisionTypeId: unique symbol = Symbol.for('@systemfsoftware/effect-daemon/RestartDecision')
//   ^ a mutant flipping this string survives every test — it is identity data

export class RestartDecisionRestart extends S.TaggedClass<RestartDecisionRestart>()('Restart', {
  indices: S.NonEmptyArray(S.Int),
}) { // the 'Restart' tag and the field schema are declarations, not decisions }

// kill zone — the decision itself
export const decideRestart = Workflow.make(
  (command: DecideInput): Result ⇒
    Match.value(command).pipe(
      Match.when({ exitSuccess: true }, () ⇒ Result.succeed(RestartDecisionContinue.make())),
      Match.when({ exitSuccess: false, intensityExceeded: true }, () ⇒ Result.fail(RestartDecisionExhausted.make())),
      Match.orElse(() ⇒
        Result.succeed(RestartDecisionRestart.make({
          indices: restartIndicesFor(command.strategy, command.failedIndex, command.totalChildren),
        })),
      ),
    ),
)
A mutant in the kill zone — say, swapping the first arm's succeed for fail — changes the decision for every input where exitSuccess is true. A property test generating that input kills it. A mutant in the disposal zone — flipping 'Restart' to '' or emptying the tag string — touches identity data no behavior reads. Those two populations are handled by different mechanisms, and the score is only honest because both are explicit.

3. The four legs that make 100 reachable

Leg 1 — Shape: one path, no hideouts

A workflow is core-regime by decree (CONSTITUTION I.6): one path — cyclomatic complexity 1 — choice as exhaustive dispatch over a closed type, iteration as map/fold, no if/?:/&&/for, no runtime import, no clock, no randomness. The corpus ruling two-regimes-core-shell (B4) names the shape's payoff directly: the CC=2 defensive guard is "the canonical breeding ground of equivalent mutants." A dead branch or a vestigial guard is exactly where a mutant survives with no observable difference. One path means every mutant changes observable behavior on some input — there is nowhere to hide.

The one admitted exception: at most one defensive guard, the first statement, converging immediately, carrying a producer-side property test proving the guard unreachable. The guard and its mutation disposition are one ruling, never two.

Leg 2 — Killers: the type is the generator

The tests that kill the arm mutants are property tests (CONSTITUTION III.2): the input type generates its own inputs. DecideInput is a closed domain — exitSuccess × intensityExceeded × strategy × index bounds — so a property run sweeps every arm. Any behavioral mutant produces a different Result for some generated input and dies. Exhaustive dispatch over a closed domain is the shape a property suite can cover completely; that is the whole reason the two doctrines travel together.

Leg 3 — Disposal: named reasons, not silence

The equivalent-mutant residue inside declarations is removed mechanically, by the ignorers this repo ships (packages/stryker-plugins), each excision carrying a reason string that names the property it rests on:

// packages/stryker-plugins/src/effect-schema-ignorer/schema-declaration-ignore.kernel.ts
export const SYMBOL_DESCRIPTION_IGNORED = 'Symbol.for() brand description is identity-only data, not behaviour'
export const TAGGED_TAG_IGNORED     = 'TaggedClass/TaggedError _tag is a declaration discriminant, not behaviour'
export const TAGGED_FIELDS_IGNORED  = 'TaggedClass/TaggedError field schema is a declaration, not behaviour'
export const CLASS_ID_IGNORED       = 'Schema.Class identifier is a declaration name, not behaviour'
The disposal channel is calibrated, and its history is the proof it is honest in both directions. Annotations that alter behavior — arbitrary, message, jsonSchema, pretty, equivalence, parseIssueTitle — are deliberately not ignored: a surviving mutant of one is a test gap, never an equivalent mutant. And a Schema.Class-fields rule was tried, turned fourteen survivors green in one run, and was removed — it was hiding accepted-value-set decisions the survivors were pointing at. Disposition rules get deleted when they overreach; that is what makes them dispositions rather than suppression.

Leg 4 — Audit: the killers must have earned their place

A kill-count alone certifies nothing — an implementation-mirroring test kills every mutant and tests nothing (the mutation-loop-llm-architecture-fit ruling names this as the oracle's blind channel). So the run is audited after the fact by packages/stryker-js/mutation-run/src/test-contribution.ts, under disableBail: true so every killing test is recorded:

  • A property-test file that kills nothing unique — every mutant it kills, another file also kills — fails the run. Each test must defend something only it defends.
  • A timeout kill arrives with killedBy: [] — real, attributable to nobody. The file is ruled unmeasurable, not toothless: nobody is spared on an unplaced kill.
  • Under bail mode the gate refuses a verdict entirely rather than accusing on partial evidence.

4. What the config actually says

// packages/effect-daemon-spec/stryker.config.json
{
  "mutate": [ "src/**/*.workflow.ts", "src/**/*.schema.ts" ],
  "ignorers": [ "effect-schema-declarations", "in-source-vitest-block" ],
  "thresholds": { "high": 100, "low": 100, "break": 100 },
  "disableBail": true
}
Read it against the diagram: mutate names the population, ignorers names the disposal channel, break: 100 is the killed-or-disposed claim, disableBail: true is what makes the contribution audit possible.

5. Why the filename suffix was never the mechanism

The corpus ruling mutation-score-scope puts the last piece straight: break=100 is a claim about its glob. The score certifies the files inside mutate and says nothing about the complement. The .workflow.ts suffix was only ever the population picker — it chose which files the gate covers, and the gate did the rest.

That is why deleting the suffix taxonomy costs the mechanism nothing, provided one thing moves with it: the population list. The plan replaces the glob with an enumerated list of exact paths, and — the part your question forced in — the list carries the whole core regime, not just the mutation run. The one-path gate that today reads filename.endsWith('.workflow.ts') re-keys to the same list. Without that re-keying, a listed file could grow an if guard, equivalent mutants would breed in it, 100 would become unreachable, and the gate would get narrowed until it passes — the exact failure the taxonomy's deletion is supposed to make impossible.

The whole mechanism in one sentence: a one-path shape leaves equivalent mutants nowhere to live, properties over the closed domain kill every mutant that is real, the ignorer disposes the declaration residue by named rule, the contribution audit keeps the killers honest — and 100 means killed-or-disposed, because the literal 100%-killed is a number undecidability will never let you verify.
