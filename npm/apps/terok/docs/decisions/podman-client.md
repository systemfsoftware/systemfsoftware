# Decision: How TypeScript talks to Podman

Status: proposed
Date: 2026-08-11
Scope: `npm/apps/terok` — the from-scratch TypeScript/Effect-TS reimplementation of terok, a Podman-native sandbox runtime for AI coding agents (Node/Bun on Linux). Ships a CLI, a full TUI, and kernel-level egress enforcement.

## Decision

Talk to Podman through its **Docker-compatible REST API on the unix socket, using `@effect/platform`'s HttpClient with an undici dispatcher configured for the socket** — `NodeHttpClient.makeUndici(new undici.Agent({ connect: { socketPath } }))` — verified working against podman 6.0.2 in this session. The HTTP transport (undici) and the server side (podman's `system service` compat API) are both maintained; the only code we write is a thin, typed compat-API endpoint layer, which the repo's cell doctrine would author as an adapter anyway.

The **podman CLI binary stays as the defined fallback** for the three enumerable gaps the compat API cannot express, each verified in this session:

1. Rootless network-mode detection — terok probes `podman info -f '{{.Host.RootlessNetworkCmd}}'`; podman 6.0.2's compat `GET /info` returns a flat Docker-shaped struct with **no `Host` object and no `RootlessNetworkCmd`** (verified by probing the live socket).
2. The `--hooks-dir` passthrough escape hatch (`run.podman_args` in project.yml) — OCI hooks otherwise ride on the host-side `containers.conf` patch terok-sandbox performs at install time, which needs no per-run flag.
3. Interactive TTY `exec`/attach — the compat API requires the HTTP/1.1 upgrade hijack protocol for attached streams; the CLI's `podman exec -it` / `podman run -it` with a PTY is the battle-tested route, and the CLI fallback exists anyway.

Operationally the port must ensure the socket is live (`systemctl --user enable --now podman.socket`, or `podman system service`), and fall back to the CLI when it is not — a rootless host does not run the socket by default.

## Candidates considered

1. **undici via `@effect/platform` HttpClient (compat API over unix socket) — CHOSEN.** `@effect/platform-node`'s `NodeHttpClient` exposes a `Dispatcher` injection point (`makeUndici(dispatcher)`, `layerUndici`, the `Dispatcher` context tag) and undici's `Agent`/`Client`/connector accept `socketPath`. Empirically verified in this session against podman 6.0.2: `GET /version` → 200 (Docker ApiVersion 1.44), `GET /_ping` → 200 "OK", `GET /containers/json` → 200. Zero foreign dependency (undici is Node's own HTTP stack; the codebase already depends on `@effect/platform` 0.97.1 / `@effect/platform-node` 0.108.1), typed errors, Effect retry/timeout middleware, `Effect.Stream` for the events/logs/build streams.
2. **dockerode 5.0.1 — runner-up.** Actively maintained (npm modified 2026-06-24; 7 releases in the last 12 months), `socketPath` option flows into `http.request({ socketPath })`, and it works against podman — verified in this session (`info()`, `listContainers()`, `version()`, `ping()` all OK on podman 6.0.2). It is what the Podman team's own product ships. **Why it lost:** it is a foreign promise/callback API inside an Effect-TS codebase — every call needs an adapter layer, the type surface is Docker-shaped (partial `@types/dockerode`), and it buys exactly one thing we verified we do not need from it: pre-built exec-hijack machinery, which we route through the CLI anyway. Choosing it would add a dependency whose entire value duplicates code the port already has a reason to write.
3. **Shelling out to the `podman` binary — what the Python terok actually does; third.** This is the parity-exact surface (see below), needs zero socket setup, and covers 100% of terok's probes. **Why it lost for the TS port:** the original's own code treats it as a cost — per-probe subprocess spawns with `-f` format-string parsing, a TUI freeze fixed by adding probe timeouts (terok#1181), and a `podman ps` batch written specifically to avoid per-container inspect N+1s. The API returns the same data as JSON in one round trip through the same `HttpClient` as everything else, with streaming (`/events`, `/logs?follow=1`, build progress) instead of long-lived parsing subprocesses. It remains the fallback, not the primary.
4. **`@balena/dockerode` — disqualified: it does not exist.** npm registry returns HTTP 404 for `@balena/dockerode` (checked 2026-08-11). The historical balena fork evolved into `docker-toolbelt` (balena-io-modules, npm latest 7.0.6, a dockerode **wrapper** with balena-specific helpers, deps JSONStream/tar-stream/randomstring), and balena's own `balena-cli` now depends on upstream `dockerode` `^4.0.5` + `docker-modem` `^5.0.6` (PR #2754 "Upgrade dockerode and docker-modem dependencies"). The fork's successor uses canonical dockerode.

## What comparable projects actually ship

Read from package manifests, npm registry entries, and source on 2026-08-11 (terok clones in `/tmp`, made read-only; local packages read from this repo's pnpm store):

- **The Python terok (behavioral spec of the port) talks to Podman exclusively through the CLI binary via subprocess — never the REST API.** `terok-sandbox`'s `runtime/podman.py` (pinned wheel `terok_sandbox-0.5.0a20`) opens: "Every `subprocess` call that ends in a `podman` invocation lives in this module" — `podman inspect -f`, `podman ps`, `podman info -f`, `podman run/start/stop/rm/exec/logs/events/cp/build` all via `subprocess`. terok's own `lib/orchestration/task_runners/shield.py` calls `subprocess.check_output(["podman", "container", "inspect", "-f", "{{.Id}}", "--", cname])` directly. The unit tests patch `terok_sandbox.runtime.podman.subprocess.check_output`. The only socket in the podman module is a local TCP port reservation (`PodmanPortReservation`), not the API.
- **podman-desktop — the Podman team's own product — ships `dockerode`.** `containers/podman-desktop` `packages/main/package.json` (main branch, read 2026-08-11): `"dockerode": "^5.0.1"`. The team that writes podman drives its full GUI (run/exec/logs/build/events) over the compat API with dockerode, not by shelling out.
- **balena-cli** — `balena-io/balena-cli` `package.json` (master): `"dockerode": "^4.0.5"`, `"docker-modem": "^5.0.6"`. The originator of the dockerode fork uses upstream dockerode.
- **npm has no maintained Podman-specific TypeScript SDK** — npm search for "podman api client" / "podman rest" returns only `@podman-desktop/tests-playwright` (a test harness) and unrelated packages. There is nothing maintained to adopt instead of one of these four surfaces; the "hand-roll" is limited to the endpoint layer, and every comparable project ships exactly such a layer (dockerode around the same API).
- **Podman's own side** (verified on this machine, podman 6.0.2): `podman system service` accepts `unix://` URIs and supports systemd socket activation; the rootless user socket is `ListenStream=%t/podman/podman.sock` (`%t` = `$XDG_RUNTIME_DIR`, e.g. `/run/user/1000/podman/podman.sock`), the rootful one `/run/podman/podman.sock`. `GET /version` on the live socket reports Docker `ApiVersion: 1.44`, `MinAPIVersion: 1.24` — the compat API speaks Docker-versioned protocol, so unversioned dials (what dockerode sends unless told otherwise) and `/vX.Y.Z` paths both work (both verified 200).

## Deciding criterion

**Minimum integration distortion while keeping every transport and protocol layer on a maintained implementation, with Podman rootless-socket support and a narrow, enumerable fidelity gap.**

Concretely: (a) the transport and server must be maintained — undici is Node's own HTTP stack (8.10.0 in this repo's store), podman's compat API is the surface podman-desktop drives in production; (b) the client must be the codebase's own abstraction — the repo is Effect-TS throughout and already depends on `@effect/platform` 0.97.1, so `NodeHttpClient` + a socketPath dispatcher is zero distortion, while dockerode would be a foreign callback/promise library behind an adapter for no functional gain; (c) rootless socket support — proven for both undici (connector `socketPath`) and dockerode (`socketPath` option); (d) the gap vs. the original's CLI surface must be enumerable — it is exactly three items (RootlessNetworkCmd probe, `--hooks-dir` escape hatch, interactive TTY exec), all covered by the CLI fallback the port needs anyway. A candidate that needs a hand-rolled HTTP stack, or that cannot express the launch path, or that adds a foreign API layer without closing a gap, loses.

## What would reverse this

The one real risk of the undici route is the compat API's **exec hijack / attached-stream protocol** (HTTP upgrade + multiplexed stream) if interactive exec ever moves onto the API. The reversal observation: if a spike against the target podman matrix shows the hand-rolled hijack or stream demux misbehaving (upgrade mishandling, 8-byte frame demux errors, `Tty`-mode corruption), or if podman compat-API gaps beyond the three enumerated ones surface during the port (a fourth probe that cannot be expressed), **reverse the primary to dockerode 5.0.1 against the same socket** — it is podman-desktop-proven for exactly the exec/build/events machinery, keeps the identical socket and API, and the adapter layer the doctrine would write anyway absorbs it. Secondary reversal: if socket availability proves operationally unreliable on target hosts (socket service not enabled, `podman.socket` masking), elevate the CLI to primary — that is the Python original's exact surface and has zero setup cost.
