# Decision: TUI framework for the terok task dashboard

Status: proposed
Date: 2026-08-11
Scope: `npm/apps/terok` — the from-scratch TypeScript/Effect-TS reimplementation of terok, a Podman-native sandbox runtime for AI coding agents (Node/Bun on Linux). The TUI is a live multi-pane task dashboard with streaming logs — not a wizard.

## Decision

Build the terok TUI on **OpenTUI** — `@opentui/core` + `@opentui/solid` (SolidJS reconciler) + `@opentui/keymap` — the exact stack the opencode agent TUI ships today. Pin it in the workspace catalog and an `overrides` entry (mirroring opencode's `script/upgrade-opentui.ts` workflow), because the library is fast-moving (0.4.4 → 0.5.1 between 2026-07-16 and 2026-08-04, plus daily snapshot builds) and must be upgraded deliberately, not drift-loose.

Terok's TUI is a multi-pane live dashboard (projects + tasks + worker log panes with streaming output, kernel-egress shield status, vault/clearance screens — the Python original is a Textual `App` with left/right panes, screens, workers, and tmux integration). The requirement profile is: full-screen layout, focus handling, redraw performance under streaming content. OpenTUI is the only maintained candidate built for exactly that profile and proven by the single most comparable product.

## Candidates considered

1. **OpenTUI** (`@opentui/core` + `@opentui/solid` + `@opentui/keymap`) — **CHOSEN.** Native Zig core with TS bindings, imperative core + SolidJS reconciler, component/layout primitives, scrollback with syntax highlighting, mouse + Kitty keyboard protocol, keymap engine, 60 fps renderer. Actively maintained: anomalyco/opentui 12,950 stars, last push 2026-08-11 (today), MIT; npm `@opentui/core` 0.5.1 modified 2026-08-11.
2. **Ink (React for CLIs)** — runner-up. Battle-tested for streaming prose (gemini-cli, Claude Code, Cloudflare Wrangler per opencode's own issue). **Why it lost:** its strongest adopters run it for single-pane conversation/prose flows; gemini-cli ships it only as a fork (`"ink": "npm:@jrichman/ink@6.6.9"`) and reimplemented focus/keypress entirely (`ui/hooks/useFocus.js`, `useKeypress`, `KeypressContext`); no multi-pane dashboard precedent at opencode's scale — opencode itself uses Ink only for its _lite_ (non-full-screen) `oclite` UI.
3. **`@oh-my-pi/pi-tui`** (17.2.14, the omp/pi-agent TUI) — ecosystem-native, differential rendering with CSI 2026 flicker-free output, ScrollView/TabBar/Markdown/Box components, tmux integration. **Why it lost:** conversation-centric component set (editor + transcript); no declarative layout engine — components return `string[]` lines and manage width themselves, so a multi-pane dashboard is hand-rolled layout; version churn at 17.x.
4. **`@effect-tui/core`** — the Effect-native option. **Why it lost:** dead — npm 2.0.1 last modified 2026-01-27, and the canonical repo `kitlangton/effect-tui` returns HTTP 404 (confirmed via GitHub API 2026-08-11). It was low-level primitives only (CellBuffer, Palette, Colors, Keys, springs) — no layout engine, no focus model, no widgets; its own sibling `@effect-tui/react` supplies React as the renderer.
5. **blessed / neo-blessed** — **Why they lost:** dormant/dead — chjj/blessed last push 2024-03-22, embarklabs/neo-blessed last push 2021-04-24 (410 stars); Node-0.10-era API with no Kitty keyboard protocol, no CSI 2026 atomic output, no truecolor-first rendering. Not viable for a 2026 full-screen dashboard.
6. **`@clack/prompts`** — **Why it lost:** it is a prompts library ("text, password, confirm, select, autocomplete, multiselect, spinner" — "80% smaller than other options"), not a full-screen framework; no layout, no focus model, no streaming panes. The requirement explicitly excludes a wizard.

## What comparable projects actually ship

Read from package manifests and source on 2026-08-11 (clones in `/tmp`, made read-only):

- **sst/opencode (anomalyco/opencode)** ships its full TUI on **OpenTUI**. Root `package.json` catalog pins `@opentui/core`/`@opentui/solid`/`@opentui/keymap` at `0.4.5` and an `overrides` block forces them repo-wide; a dedicated `script/upgrade-opentui.ts` bumps all three in lockstep. `packages/opencode` has `jsxImportSource: "@opentui/solid"`, preloads `@opentui/solid/preload`, and builds with `createSolidTransformPlugin` from `@opentui/solid/bun-plugin`. The app shell (`packages/tui/src/app.tsx`) creates the renderer via `createCliRenderer({ targetFps: 60, useKittyKeyboard: {}, autoFocus: false, exitOnCtrlC: false, useMouse: ... })` inside an Effect `Effect.fn("Tui.run")` with `Effect.acquireRelease` on the renderer and a `Deferred` shutdown — an Effect-TS codebase integrating OpenTUI under Effect scoping. `packages/tui/src/routes/session/` is the multi-pane dashboard: `sidebar.tsx` (42-col sidebar) + scrollback + footer, with scrollback syntax highlighting via `web-tree-sitter` and `@opentui/core/parser.worker`. opencode _also_ ships a second, lighter UI ("oclite") built on **Ink** (issue #11762), for a non-full-screen log-style flow.
- **gemini-cli** ships its TUI on **Ink**, but a fork: `packages/cli/package.json` has `"ink": "npm:@jrichman/ink@6.6.9"` plus `ink-gradient`, `ink-spinner`; root `package.json` `overrides` repeats the fork. `interactiveCli.tsx` calls `render(<AppWrapper/>)`; the app reimplements focus and keypress routing in local hooks (`ui/hooks/useFocus.js`, `ui/hooks/useKeypress.js`, `KeypressContext`, `KeypressPriority`) rather than Ink's built-ins — direct evidence that Ink's own focus model is insufficient for a full-screen agent UI.
- **oh-my-pi / omp** ships **`@oh-my-pi/pi-tui`** 17.2.14 (updated 2026-08-11; repo `can1357/oh-my-pi`, homepage omp.sh). The pi-coding-agent's entire UI — `TranscriptContainer`, `ScrollView`, `dashboard.ts`, session picker, settings lists — imports from `@oh-my-pi/pi-tui` (`src/autoresearch/dashboard.ts`, `src/cli/session-picker.ts`). It is a plain component framework (`interface Component { render(width): string[]; handleInput?(data) }`) with differential rendering and CSI 2026 synchronized output. The omp workspace in this repo (`omp/`) is a hook-based harness with no TUI of its own — its UI is the host terminal (Claude Code); so the harness ecosystem's _own_ TUI answer is pi-tui, and that answer is the conversation-shaped one.
- **Zed agent surface** — native GUI, not a terminal TUI: the Agent Panel is an in-editor panel (zed.dev/docs/ai/agent-panel) rendered by Zed's own GPU UI (GPUI); it can host agent CLIs in Terminal Threads, but Zed contributes no terminal-TUI framework. Not a data point for a terminal-native product.
- **The Python terok (behavioral spec of the port)** built its TUI on **Textual** — `tui/app.py` opens with "Terok TUI application built on Textual", a full-screen `App` with a left pane (`#project-list`, `#project-state`) and right pane (`#task-list`, `#task-details`), CSS layout, `Screens` (shield, vault, worker log, setup, clearance), workers, key bindings, and tmux-session integration. The TS reimplementation must reproduce this shape: multi-pane, full-screen, streaming.

## Deciding criterion

**Layout + focus + redraw performance for a live multi-pane streaming dashboard, under a maintained, dependency-shaped library.** Concretely: the framework must (a) be actively maintained (registry-modified within weeks, not years), (b) provide full-screen layout primitives plus an explicit focus/keymap model, (c) be proven in production by the most comparable workload — a full-screen agent task dashboard with streaming panes — rather than by prompt or single-pane prose apps, and (d) integrate with an Effect-TS codebase without framework-level impedance. OpenTUI satisfies all four and is the only candidate that does: (a) modified today, (b) layout + scrollback + dialogs + keymap engine + mouse + Kitty keyboard, (c) it IS opencode's production TUI (an Effect 4.0.0-beta codebase — same shape as terok), (d) opencode documents the Effect-scoped integration pattern. Ink fails (c) for a multi-pane dashboard (its flagship adopters are single-pane prose flows, and gemini-cli needed a fork + full focus reimplementation); pi-tui fails (b) for dashboards (no declarative layout engine); effect-tui fails (a) (dead repo); blessed/neo-blessed fail (a) (dormant since 2021–2024); clack fails (b)+(c) by construction.

## What would reverse this

OpenTUI's known instability under concurrent pane updates is the exposure: opencode's own tracker lists "OpenTUI causes crashes and heavy memory usage" (#3798), screen flickering (#4905, #3719, #3776), and streaming cutoffs (#5838) — several of which opencode addressed by moving its _lite_ UI to Ink. **The reversal observation:** if the first terok dashboard prototype on OpenTUI reproduces crash/flicker/high-idle-CPU under concurrent multi-pane streaming (worker logs + task lists + egress shield status updating at 60 fps), or if OpenTUI's Zig native core (per-platform prebuilt binaries, Zig toolchain requirement) becomes a packaging liability for terok's distribution, **reverse to Ink** — pinning the `@jrichman/ink` fork or our own fork following gemini-cli's pattern, and building panes on Ink's Yoga flexbox with a custom focus layer. A second, weaker reversal trigger: if terok's deployment surface becomes the omp ecosystem itself (which owns pi-tui), the ecosystem-native option becomes the better bet for consistency with the host harness.
